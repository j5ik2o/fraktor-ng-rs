# 設計課題：所有権モデル（Arc / Shared の過多をどうするか）

状態: draft（2026-11-11、ユーザー提起）。設計設定 3.4（Rust 方針）の中でも
最初に決めるべき課題として切り出す。決定ではない。

## 問題提起（ユーザー）

旧 fraktor-rs は Arc / Rc のオーバーヘッドが大きい設計になっている。
なんとかしたい。

## 実態の計量（旧 fraktor-rs `fea328f`、`modules/` 配下、grep ベース）

| パターン | ファイル数 | 出現回数 |
|---|---|---|
| `ArcShared` | 454 | 3,301 |
| `Shared<...>` | 411 | 1,528 |
| `SpinSyncMutex` | 202 | 1,685 |
| `SpinSyncRwLock` | 14 | 74 |
| `Arc<...>`（直接） | 41 | 133 |
| `Rc<...>`（直接） | 1 | 1 |

読み解き：共有所有＋内部可変性は例外ではなく**既定の構造**になっている。
clippy の disallowed-types で `Arc` / `Rc` / `std::sync::Mutex` の直接使用を禁止し
`ArcShared` / `SpinSyncMutex` 等のラッパーへ寄せるルールが、この構造を全面に広げた。
個別の clone は小さくても、アクター実行のホットパス（生成・tell・supervision・
DeathWatch）で参照カウントの原子操作とロック取得が常時走る形になっている。

## なぜこうなったか（構造的な理由）

- Pekko（JVM）は参照の共有が GC 前提でほぼ無料。そのオブジェクトグラフ
  （System ↔ Cell ↔ Mailbox ↔ Ref が互いを指す）を Rust へ素直に写すと、
  所有権が循環・多重になる箇所すべてが Arc + Mutex に落ちる
- 旧側のルール（内部可変性は Shared ラッパー経由、CQS、TOCTOU 回避のための
  `with_write` 原子化）が、ロック前提の共有をさらに後押しした
- つまり「JVM のグラフをそのまま写す」という移植方針そのものが Arc 過多の原因で、
  個別最適化（clone を減らす等）では解けない

## 対策の方向（候補、未決定）

### A. 所有権を実行境界で切る（本命候補）

- ActorCell と actor 本体は dispatcher / executor 側が**単独所有**する。
  mailbox がメッセージを所有し、実行ループが `&mut` で回す。ロックも参照カウントも要らない
- ActorRef は実体へのポインタではなく軽いハンドルにする
  （例：宛先チャネルへの sender clone、あるいは (system, actor id) の Copy な識別子＋
  レジストリ解決）。Ref の clone が原子操作にならない形を選ぶ
- 親子・supervision の所有はツリー側（親またはレジストリ）が持ち、子は親を
  Arc で指さない（必要なら id / 弱い参照相当に留める）
- DeathWatch や EventStream の購読関係は「参照の保持」ではなくレジストリへの
  登録として表す

### B. Arc を境界だけに閉じ込める

- Arc を使ってよい場所を、システム境界・拡張登録・設定など低頻度の共有に限定し、
  ホットパス（cell、mailbox、ref、メッセージ配送）では使わない、という予算を
  ルール化する。旧側の「ラッパー経由なら全面可」とは逆の発想
- 計量可能な形にする：ホットパス対象モジュールでの ArcShared 出現数を
  syn checker のルール（§切り分け文書 3節）で数え、上限を置く

### C. シングルスレッド実行の活用

- dispatcher がスレッドを固定する設計なら、セル内は `Rc` / 素の所有で足り、
  `Send` が必要な境界だけを Arc にする。ただし旧側は Rc がほぼ皆無（1件）で、
  最初からマルチスレッド前提に寄っていた。ng で前提をどう置くかは
  実行基盤の決定（3.4）と一体

## Pekko テストとの関係

- 所有権モデルは内部設計であり、Pekko テストが規定するのは振る舞い（意味論）だけ。
  テストを正に保ったまま所有権モデルは自由に変えられる。ここは「写す」対象ではなく
  Rust 側の設計判断として最初に固定すべき領域

## 決め方（案）

- スパイク向き：同一の小さなシナリオ（アクター生成→tell→応答→停止）を
  (1) ArcShared 全面型 と (2) executor 単独所有＋ハンドル型 で実装し、
  スループットと割当回数を比べる。判断メモだけ残してコードは捨てる
- 決める際の論点：dispatcher のスレッドモデル、ActorRef の表現、
  子・DeathWatch の所有の置き場所、Arc の使用予算を置くかどうか
