# 設計課題：所有権モデル（Arc / Shared の過多をどうするか）

状態: draft（2026-11-11、ユーザー提起）。設計設定 3.4（Rust 方針）の中でも
最初に決めるべき課題として切り出す。決定ではない。

## 問題提起（ユーザー）

旧 fraktor-rs は Arc / Rc のオーバーヘッドが大きい設計になっている。
なんとかしたい。

## 実態の計量（旧 fraktor-rs `fea328f`、`modules/` 配下、grep ベース）

| パターン | ファイル数 | 出現回数 |
|---|---|---|
| `ArcShared` | 454 | 3,301 |
| `Shared<...>` | 411 | 1,528 |
| `SpinSyncMutex` | 202 | 1,685 |
| `SpinSyncRwLock` | 14 | 74 |
| `Arc<...>`（直接） | 41 | 133 |
| `Rc<...>`（直接） | 1 | 1 |

読み解き：共有所有＋内部可変性は例外ではなく**既定の構造**になっている。
clippy の disallowed-types で `Arc` / `Rc` / `std::sync::Mutex` の直接使用を禁止し
`ArcShared` / `SpinSyncMutex` 等のラッパーへ寄せるルールが、この構造を全面に広げた。
個別の clone は小さくても、アクター実行のホットパス（生成・tell・supervision・
DeathWatch）で参照カウントの原子操作とロック取得が常時走る形になっている。

## なぜこうなったか（構造的な理由）

- Pekko（JVM）は参照の共有が GC 前提でほぼ無料。そのオブジェクトグラフ
  （System ↔ Cell ↔ Mailbox ↔ Ref が互いを指す）を Rust へ素直に写すと、
  所有権が循環・多重になる箇所すべてが Arc + Mutex に落ちる
- 旧側のルール（内部可変性は Shared ラッパー経由、CQS、TOCTOU 回避のための
  `with_write` 原子化）が、ロック前提の共有をさらに後押しした
- つまり「JVM のグラフをそのまま写す」という移植方針そのものが Arc 過多の原因で、
  個別最適化（clone を減らす等）では解けない

## 対策の方向（候補、未決定）

### A. 所有権を実行境界で切る（本命候補）

- ActorCell と actor 本体は dispatcher / executor 側が**単独所有**する。
  mailbox がメッセージを所有し、実行ループが `&mut` で回す。ロックも参照カウントも要らない
- ActorRef は実体へのポインタではなく軽いハンドルにする
  （例：宛先チャネルへの sender clone、あるいは (system, actor id) の Copy な識別子＋
  レジストリ解決）。Ref の clone が原子操作にならない形を選ぶ
- 親子・supervision の所有はツリー側（親またはレジストリ）が持ち、子は親を
  Arc で指さない（必要なら id / 弱い参照相当に留める）
- DeathWatch や EventStream の購読関係は「参照の保持」ではなくレジストリへの
  登録として表す

### B. Arc を境界だけに閉じ込める

- Arc を使ってよい場所を、システム境界・拡張登録・設定など低頻度の共有に限定し、
  ホットパス（cell、mailbox、ref、メッセージ配送）では使わない、という予算を
  ルール化する。旧側の「ラッパー経由なら全面可」とは逆の発想
- 計量可能な形にする：ホットパス対象モジュールでの ArcShared 出現数を
  syn checker のルール（§切り分け文書 3節）で数え、上限を置く

### C. シングルスレッド実行の活用

- dispatcher がスレッドを固定する設計なら、セル内は `Rc` / 素の所有で足り、
  `Send` が必要な境界だけを Arc にする。ただし旧側は Rc がほぼ皆無（1件）で、
  最初からマルチスレッド前提に寄っていた。ng で前提をどう置くかは
  実行基盤の決定（3.4）と一体

## 循環参照は解決できるか（2026-11-11 検討）

結論：大半は解決できる。鍵は「循環しているのは参照グラフであって、所有である
必要はない」という切り分け。JVM では GC が両者を同一視するので循環が自然に
見えるが、Rust では辺ごとに 所有／ハンドル／弱参照／チャネル へ分類し直せる。

方針の確認（ユーザー）：極力、単独所有＋ハンドル型にする。どうしても共有せざるを
得ないところだけ Arc / Rc を想定する。

### 辺ごとの解法

| Pekko/Akka の循環構造 | 辺の分類替え |
|---|---|
| ActorRef → Cell、Cell が自分の Ref を作る | Ref は実体へのポインタではなくハンドル（id＋世代）。Cell 側は自分の id を値として持つだけ。循環は「論理的な同一性」であって所有ではない |
| 親 Cell → 子 Cell 群、子 → 親（context.parent） | 所有は executor の所有テーブル（ツリー）が持つ。子が持つ親情報は親ハンドル（Copy な値）。必要時に executor 経由で解決する |
| Actor ↔ ActorContext（actor が context を保持し、context が self / system を指す） | Context を actor に保持させない。executor が処理時に `&mut Context` を**貸し出す**。self はハンドル値、system は処理系への参照をその場で渡す。保持による循環が消える |
| ActorSystem ↔ Guardian / Scheduler / 拡張機能 | ここは制御プレーンで低頻度・長寿命。共有が本当に要る辺は Arc を許容する（予算内）。ただし Scheduler 等が System を掴むのではなく、executor への送信ハンドルを持つ形にすると辺自体を消せる場合が多い |
| DeathWatch（watch する側 ↔ される側） | どちらも相手を保持しない。所有テーブル側の登録表（watched id → watcher id 群）として表す。終了時に表を引いて通知する |
| EventStream / EventBus の購読関係 | 同上。購読表は所有側が持ち、購読者はハンドルで表す |
| Dispatcher ↔ Cell（dispatcher がセルを実行し、セルが dispatcher を知る） | セルは dispatcher の id / ハンドルを持つだけにし、実スケジューリングは executor 側が所有テーブル越しに行う |

### それでも Arc / Rc が残る場所（想定として明記）

- 制御プレーンの共有：設定、拡張レジストリ、接続プール（remote / persistence の
  ジャーナル接続等）。低頻度なので原子操作のコストが問題にならない
- スレッド境界を越える送信端：シャード間チャネルの Sender 等。ただしこれは
  「境界」に閉じ込められ、シャード内のホットパスには入らない
- 戻り辺どうしても実体参照が要る場合の `Weak`（Arc/Rc の弱参照）。
  強い循環を作らず、生存確認つきで辿れる
- Rc の出番はシャード内（単一スレッド）に限る。シャードを越えるものは Arc

### 原則として言語化

- 所有は木（または所有テーブル）にする。循環させるのは所有ではなく参照だけ
- 参照は原則ハンドル（値）で表す。実体ポインタで戻る辺は Weak かチャネルに置き換える
- Arc / Rc は「置いてよい場所のリスト」で管理し、ホットパス（cell / mailbox /
  ref / 配送）には置かない

## Pekko テストとの関係

- 所有権モデルは内部設計であり、Pekko テストが規定するのは振る舞い（意味論）だけ。
  テストを正に保ったまま所有権モデルは自由に変えられる。ここは「写す」対象ではなく
  Rust 側の設計判断として最初に固定すべき領域

## 決め方（案）

- スパイク向き：同一の小さなシナリオ（アクター生成→tell→応答→停止）を
  (1) ArcShared 全面型 と (2) executor 単独所有＋ハンドル型 で実装し、
  スループットと割当回数を比べる。判断メモだけ残してコードは捨てる
- 決める際の論点：dispatcher のスレッドモデル、ActorRef の表現、
  子・DeathWatch の所有の置き場所、Arc の使用予算を置くかどうか

## スパイク結果（2026-11-11 実施）

実施場所はリポジトリ外（Muse ワークスペース `~/workspace/spikes/ownership/`）。
コードは使い捨てで、ここに残すのは判断メモのみ。計測環境は共有 CPU の VM、
rustc stable 1.99.1、依存は std のみ、両実装とも単一スレッド。

シナリオ：カウンタアクター N 個を生成し、各々に M 回 +1 を送り、合計が N×M に
なることを全 run でアサート検証（両実装とも通過）。

- 実装1「Arc全面型」：セルは `Arc<Mutex<Cell>>`、ActorRef は Arc clone を保持、
  tell ごとに clone（参照カウント原子操作）＋ロック＋同期処理
- 実装2「単独所有＋ハンドル型」：executor が `Vec<Cell>` を単独所有、ActorRef は
  `usize` index の Copy ハンドル、tell は mailbox に積み実行ループが `&mut` で処理

実測（N=100、M=10,000、総 1M メッセージ、5 run 中央値、プロセス起動3回）：

| 起動 | Arc全面型 | 単独所有＋ハンドル型 |
|---|---|---|
| 1回目 | 80.58 ms（12.4M msg/s） | 5.48 ms（182.5M msg/s） |
| 2回目 | 44.50 ms（22.5M msg/s） | 5.68 ms（176.2M msg/s） |
| 3回目 | 50.30 ms（19.9M msg/s） | 7.26 ms（137.7M msg/s） |

N=1,000 / M=1,000（総 1M）でも Arc 48.98 ms 対 単独所有 5.60 ms で傾向不変。
**単独所有型が中央値で約7〜15倍（保守的に約1桁）速い**ことが3回すべてで再現した。

割当：Arc全面型はセル生成ごとに Arc 割当（N+1 回）。単独所有型は回数が N に
よらず3回（ただし mailbox を `with_capacity(N×M)` で一括予約した約16MB を含む。
回数は O(1) だが予約メモリは大きい、という容量政策側のトレードオフ）。
メッセージごとの割当は両実装ともゼロで、差は原子操作＋ロック vs キュー操作に出た。

### 結論

- **単独所有＋ハンドル型を本命にしてよい**。Arc は全面禁止ではなく、executor／
  スレッド境界や拡張登録など低頻度の共有に閉じ込める（方向 B と整合）
- 留保：(1) 単一スレッド計測のみ。マルチスレッド時の競合コストと、単独所有型の
  並列化に要る executor シャーディングの境界コストは未計測
  (2) 処理が加算のみのため比率は上限寄り（絶対差は残る）
  (3) mailbox の一括予約は実装2に有利な条件で、容量政策を変えた再測は未実施
  (4) tell 同期処理とキュー遅延処理ではレイテンシの形が別物（比較は総時間同士）
- 次に検証すべきは並列化モデル（シャーディング境界コスト）と mailbox 容量政策。
  この2つが決まれば所有権モデルは設計として固定できる
