# DGX Spark 運用ルール（新）

オーナー指示（2026-11-12）で新設。Spark の利用に関する従来ルール（同時実行の上限など、暫定として置かれていたもの）は本ルールに置き換える。

## 1. 基本姿勢

- Spark（DGX Spark x4、DeepSeek V4.1 Flash、vLLM）は「空いているのが普通」ではなく「ある程度使われているのが普通」の設備として扱う。待機水準（4台合計 約157W、消費電力ベース）が続く状態は、使えていない状態とみなす。
- 稼働率は sparkDash（http://10.0.1.30:5555）と Grafana（同 3000）で見える。横断の朝サマリに稼働の1行を入れる。形式は「Spark: 現在 ○○W / 24h出力 ○○万トークン（24h電力量 ○.○kWh）」とし、出典は sparkDash の `/api/fleet-energy`（`currentWatts30s`、`outputTokens24h`、`energy24hKwh`）。この API は LAN 専用なので、取得は Mac mini 経由（SSH で mini 上から curl）で行う。初出は 2026-11-12 夜の本スレッド引き継ぎ分（下記 §5）。

## 2. 役割分担（控えではなく分担）

- 手順が固定できる作業（実装、検証、読み取り、量のある処理、事前分解した在庫の実行）は、既定で Spark 側（DeepSeek）へ寄せる。
- 判断・設計・契約（contract）にあたる仕事は強いクラウドモデル側に置く。これは使用量の抑制ではなく、品質のための分担である。
- クラウド側の枠（rate limit）が詰まった時間帯は、Spark 側の在庫実行でラインを止めない。

## 3. 同時実行（全体予算と水位計）

オーナー決定（2026-11-12 夜）で改定。従来の「目安は並行8」は、ラインごとの目安としては廃止する。

### 3-1. 全体予算 16

- 同時実行の予算は **DGX 全体で 16** とする。これはラインごとの権利ではない。coordinator は6ライン（fraktor、corporate-site、modern-ddd-book、ddd-principles、ESA、PPD）あり、各ラインが「8」を自分の権利として解釈すると最大48になり、実測の裏付け（単独で並行16まで）を超えるため、予算は横断側（DGX Spark 運用スレッド）で一元管理する。
- 各ラインは予算16の内側で自由に使う。委任のたびの申告・許可取りはしない。ライン単独で8を超えても、全体が予算の内側なら問題ない。
- 実行の同時性はサーバ側でも固定されている：本番 vLLM は `--max-num-seqs 16` で起動している（2026-11-12、spark1 のプロセス引数で実物確認）。つまり同時に実行されるリクエストは誰が何件投げても16を超えず、予算超過は「実行」ではなく vLLM 内部の**待ち行列**として現れる。制御できないのは行列の長さと順序（ライン間の優先度は無い）であり、被害は計算資源の奪い合いではなく応答遅延の膨らみとして出る。予算16を変更する場合は、この起動引数の変更と vLLM 再起動がセットになる（ルールの文面だけでは変わらない）。
- 根拠は §5 の実測：短い入出力では並行8まで線形（遅延悪化なし）、長い入力でも並行16まで合計 tok/s は伸び続け、1件あたりの速度に大きな低下は無かった。急な膝は16までには無い。逆に短い入出力の並行16〜32では1件あたりの速度が半分ほどに落ち始めるため、当面の予算は16に置く。
- 予算を変えたくなったら、文章で議論せず実測して決める（並行数を振って合計スループットと1件あたり速度を見る）。実測結果は §5 に追記し、予算の変更は横断側から全 coordinator へ再配布する。

### 3-2. 見張りはリースではなく水位計

- 予約・貸し出し台帳（リース）は作らない。見張りは「実態」を1か所で読む水位計だけにする。数えるのはラインの申告ではなく、vLLM 自身のメトリクスと sparkDash の実績値である。
- 読み先（2026-11-12 確立）：
  - vLLM `/metrics`：Muse VM から Tailscale トンネルプロキシ（`HTTPS_PROXY` のポートを 3130 に変えたもの）経由で `http://100.121.40.66:8000/metrics` を読む。既定の egress プロキシ（3128）経由だと Empty reply になり読めない（これが「tailnet 経由で読めなかった」件の原因）。使う指標は `vllm:num_requests_running`（実行中）、`vllm:num_requests_waiting`（待ち）、`vllm:generation_tokens_total`（差分から生成 tok/s を算出）、`vllm:kv_cache_usage_perc`。
  - sparkDash API（`/api/fleet-energy` 等）：LAN 専用のため Mac mini 経由（SSH で mini 上から curl）でのみ読む。電力と24hトークンの出典はこちら。
- 見張りの実装はフック `dgx-spark-watch`（120秒間隔、本スレッド宛て）。次が**持続したときだけ**起こす（瞬間値では起こさない）：
  - 待ちリクエスト（`num_requests_waiting` > 0）が3回連続
  - 飽和（実行中が上限16に張り付き、かつ待ち行列がある）が3回連続 ※実行中は `--max-num-seqs 16` で固定され16を超えないため、「16超え」ではなく飽和＋行列で見る（2026-11-12 に見張り条件を修正）
  - 実行中8以上で、1件あたり生成速度が 10 tok/s 未満で3回連続
  - エンドポイント到達不能が5回連続
- 劣化が続いたと知らせが来たら、対応はライン側の間引き（同時委任を減らす、在庫実行を後ろにずらす）で行う。見張り側で自動で止めたり順番待ちさせたりはしない。調停もしない。
- 旧プロファイルや指示書に残る「同時2まで」「目安は並行8（ラインごと）」等の記述は、本ルールが優先し、理由に使わない。各 coordinator は自分の指示書・プロファイル側の該当記述を本ルールに合わせて直す。

## 4. 見回り・掃除

- 見回り（patrol）とゴミ掃除（garbage-sweep.md）は Spark 側で回す。クラウド枠を使わない。
- coordinator は、Spark で回せる定型処理（棚卸し、状態確認、掃除）を見つけたらクラウド側に置かず Spark 側へ移す。

## 5. 実測の記録

- 2026-11-12：並行 1/4/8 で 41 / 167 / 369 tok/s（出力 約220トークン、遅延中央値 4.5 / 4.4 / 4.2 秒）。同時実行で遅延は悪化しない。
- 2026-11-12 追加実測（短い入出力、出力 約220トークン）：並行16で合計 152 tok/s・1件あたり 19 tok/s、並行32（実リクエスト16）で合計 226 tok/s・1件あたり 23 tok/s。合計はまだ伸びるが、1件あたりは並行8時点（約46 tok/s 相当）から半分ほどに低下する。
- 2026-11-12 追加実測（長い入力 727トークン＋出力 約500トークン）：並行1で合計 20 tok/s、8で 136 tok/s、16で 179 tok/s と16まで合計は伸び、1件あたりは 18→17→22 tok/s で大きな低下なし。急な膝は16までには無い。
- 2026-11-12 21:25 時点の稼働：4台合計 約157W（待機水準）、直近24時間の出力 約281万トークン。
- 2026-11-12 21:42 時点の稼働（sparkDash `/api/fleet-energy`、mini 経由）：現在 254W（作業中水準）、直近24時間の出力 2,828,094 トークン（約283万）、24h電力量 4.43 kWh。同日同時刻の vLLM メトリクス：実行中 2、待ち 0、KV キャッシュ使用率 約1.6%。
- 2026-11-12：vLLM `/metrics` の読み方を確立。Muse VM からは Tailscale トンネルプロキシ（ポート3130）経由で `http://100.121.40.66:8000/metrics` が読める（86KB、Prometheus 形式）。既定 egress プロキシ（3128）経由は Empty reply で、これが従来読めなかった原因。
