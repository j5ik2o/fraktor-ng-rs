# 決定：速さより Pekko の意味論を優先する

状態: **accepted（2026-11-26、オーナーが決定、元帥の項目 420）**。

## 決定

速さより Pekko の意味論を優先する。

- 意味論とは、Pekko のテストと文書が利用者に約束している振る舞いのことである。中の作りは自由である
- Pekko のテストと文書が許している振る舞いの範囲の中で、選べる振る舞いを狭めることは、ずれにしない（例：#234 の設計の
  I6。閉じたあとに来たものを取りこぼさず、dead letters へ送る）。利用者が頼れる形で約束を足すこと（文書に書く、公開 API の
  型で保証する）は、ずれとして扱う。スレッドモデルやメールボックスの作りが Pekko と違うことで生まれる強さ（今の 1 スレッドの
  実行器の同期や全体の順）は、狭めではなく作りのずれなので直す
- 速くするために意味論を弱めたり強めたりする案は採らない
- JVM・Scala に固有の振る舞いは、1 件ずつオーナーに伺う

上の 2 つ目の項目（許している範囲の中で狭めること、約束を足すこと、作りのずれ）は、オーナーの言葉ではなく、元帥が補った
文である（元帥、2026-11-26。オーナーに報告済み）。最初の版の「Pekko より強い保証も、意味論のずれとして直す」を、この形に
絞った。狭めた振る舞いは、利用者への約束として公開 API の文書に書かない（#234 の I6 も書かない）。

## オーナーの言葉

「遅くなっても今は意味論を重視して Pekko と同じスレッドモデルにする。これはスレッドモデルに限ることではない。
意味論を担保しないと移植自体が破綻しかねないから、この指針は他の場合でも適用される」

## 適用の範囲

すべての移植に適用する。スレッドモデル（[Issue #234](https://github.com/j5ik2o/fraktor-ng-rs/issues/234)）に限らない。

## この決定から出てくること

- 速さは測って報告するが、速さを理由に作業を止めない。作業を止めるのは、正しさの条件（移植した Spec、既存のテスト、
  Quint の不変条件、決定文書の正しさの条件）だけである
  - 最初に当てはめた例：#234 の設計 `docs/design/issue-234-multithread-executor.md` の §7.5 と、所有権モデルの決定文書
    `docs/decisions/ownership-model-arc-overhead.md` の改訂の条件 5
- 速くするための工夫は、意味論を変えない範囲で入れる。判断の例は、#234 の設計の §3.8 にある
- 移植の規約の要約（`.takt/facets/knowledge/fraktor-porting-rules.md`）への 1 行は、別の PR で入れる
