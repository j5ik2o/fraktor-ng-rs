# クレート構成の比較（案A 写像型／案B 層型／案C 写像ベースのハイブリッド）

状態: draft（2026-11-11）。設計設定ドラフト 3.3 と 3.4 の残件。決定ではない。
数値は baseline 台帳（Pekko v1.7.1）から再計算した。

## 前提になる事実

- 主ソースを持つモジュールは 29（計 474,887 行）。内訳の上位は stream 75,064 行、
  remote 68,021 行、actor 61,130 行、distributed-data 53,210 行、cluster 32,105 行
- ただし 29 の中には、ライブラリ本体ではないものが混ざる。bench-jmh（ベンチマーク、
  8,990 行）、multi-node-testkit（multi-JVM 用のテスト基盤、8,453 行）、docs
  （2,458 行）、osgi（440 行）、slf4j（208 行、ロギングのバインディング）、
  serialization-jackson（1,991 行、Jackson バインディング）など
- テストのみのモジュールが 10 ある（actor-tests 177、stream-tests 254、
  actor-typed-tests 117、persistence-typed-tests 50 など）。Pekko でテストが
  別モジュールなのは sbt の都合であり、Rust の慣習とは合わない
- モジュール依存は 152 辺で循環が無い。台帳のロールアップはモジュール単位で
  定義済み（承認済みグラフモデル）

## 案A：Pekko モジュール写像型

主ソースを持つモジュール1つにクレート1つを対応させる。テストのみのモジュールも
テストクレートとして写す。

- 長所：台帳のモジュールとクレートが 1 対 1 で、対応の監査が目で追える。
  `write_scope` は（モジュール, パッケージ）から機械的に導ける。クレート間の
  依存が Pekko のモジュール DAG を写すので、変な層違反はコンパイル時に出る。
  クレートが小さい単位に分かれるため、TAKT のゴール同士の書き込み衝突が起きにくく、
  コンパイルも並列に回る
- 短所：クレート数が 39 近くになり、ワークスペースの管理と公開 API の表面積が
  大きくなる（クレートをまたぐ内部ヘルパは pub にせざるを得ない）。
  JVM／sbt 都合の分割（osgi、slf4j、bench-jmh 等）まで写してしまう

## 案B：層型（旧 fraktor-rs 型）

ドメイン（actor / stream / persistence / remote / cluster 等）ごとに、core と
adaptor のような層でクレートを切る。Pekko のモジュール区切りは写さない。

- 長所：クレート数が少なく、Rust らしい境界を設計できる。内部共有は
  `pub(crate)` で済む。no_std の層を置くなら自然な形になる
- 短所：Pekko 側（モジュール, パッケージ）から Rust 側の書き込み範囲への
  対応表を別途つくり、維持し続ける必要がある（Fable 提案でも案Bの前提として
  指摘された）。台帳のモジュール合格率とクレート境界が一致しないため、
  進捗の対応は台帳の欄だけで担保することになる。旧 fraktor-rs では、この種の
  構造ルールの維持自体が重い統制装置になった、という実績がある

## 案C：写像ベースのハイブリッド（推奨）

基本は案Aの写像とし、写さないものを「モジュールごとの判断」ではなく
カテゴリ規則で決める。

1. **ライブラリ本体のモジュールは 1 対 1 でクレートにする**（`fraktor-actor`、
   `fraktor-actor-typed`、`fraktor-testkit`、`fraktor-stream`、`fraktor-remote`、
   `fraktor-cluster`、`fraktor-persistence` 等。実質 23 前後）
2. **プラットフォーム／バインディング系は畳む**。osgi は対象外、slf4j は Rust 側の
   ロギングファサード（log / tracing）への接続として actor 側に吸収、
   serialization-jackson は serde バインディングとして後段の任意クレート、
   bench-jmh は benches へ、multi-node-testkit は当面対象外（multi-JVM は
   ノード集合の外、という既存の線引きと一致）
3. **テストのみのモジュールはクレートにしない**。移植したテストは、検証対象の
   クレートの `tests/` 配下に、ノード（テストクラス）1件＝ファイル1件で置く。
   台帳の `rust.test_file` がそのパスを持つ。actor-tests のように複数クレートに
   またがるものは、主たる検証対象（actor）の tests に置き、testkit 等は
   dev-dependency で使う
4. **`write_scope` の導出規則を固定する**。ゴールの Pekko（モジュール,
   パッケージ）は、実装モジュールならそのクレート、テストモジュールなら
   規則 3 の置き場所、という機械変換で Rust 側の範囲になる

この形の効き目：

- ノード＝テストファイル＝コンパイル単位（integration test はファイルごとに
  別ターゲット）になる。Fable 提案のリスク 6「1ノードのコンパイルエラーが
  他ノードの red 判定を巻き込む」が、構造でほぼ解ける
- 対応表は「カテゴリ規則」として有限に閉じる。案Bのような対応表の継続維持が
  要らない
- クレート境界が Pekko の DAG を写すため、TAKT の並行ゴールの衝突管理と
  コンパイル並列の両方に効く

残る弱み（案Aと共通）：

- クレートをまたぐ内部ヘルパは公開 API になる。対策は、公開面を意図して設計し、
  内部用は `#[doc(hidden)] pub` のような逃がしを規約化すること（syn checker の
  対象候補）
- Pekko のモジュール分割が粗い場所（distributed-data 53,210 行が 27 ファイル等）
  は、クレート内部のパッケージ構成で受ける。クレートを割る判断は後からでもできる

## 他の決定との関係

- 所有権モデル（accepted）：executor は fraktor-actor の内部に置く。シャード境界の
  チャネルも同じクレート内で閉じるので、案Cと競合しない
- 実行基盤の暫定方針：境界実装の差し替えはクレート内部の話であり、構成に影響しない
- no_std（未決定）：要求することになった場合、案Cでは「クレート内部を kernel と
  標準層に分ける」形で受ける。最初から adaptor クレートに割る案Bよりは後付けになる
  が、割る対象がクレート単位で見えているため、移行は局所的になる

## port & adapter との関係（直交する軸）

旧 fraktor-rs の core / adaptor-std 分割の本質は、クレートの切り方そのものではなく
**port & adapter（依存性逆転）**である。core は no_std でプラットフォームに触れず、
時刻・スケジューリング・IO 等は port（トレイト）として core が定義し、具体実装は
adaptor が持つ。この観点は上の3案と直交する。案は「横の切り方（どのモジュールを
どのクレートに）」を決め、port & adapter は「縦の切り方（クレート内部の依存方向）」
を決める。したがって案Cを採っても、port & adapter は別途かけることができる。

port & adapter が ng で効く具体的な理由は、no_std そのものよりも先に2つある。

1. **テストの決定性**。Pekko テストには時間依存が大量にある（`Thread.sleep` 295 回、
   `eventually` 108 回、`TimingTest` タグ 271 件）。Clock と Scheduler を port に
   すると、仮想時間の adaptor で置き換えられ、時間依存テストの移植が決定的になる。
   これは「正はテスト」という進め方の成否に直接効く
2. **実行基盤の暫定方針そのものが port である**。「executor は自前、境界実装は
   差し替え可能」という暫定は、スケジューリングを実行基盤への port 越しに置く
   ことと同義である。port を切らないと、暫定方針は文書だけの約束になる

適用の粒度には3段階ある。

- **段階1（クレート内モジュール＋syn checker）**：各クレート内部を kernel
  （プラットフォーム非依存、port を定義）と adaptor（std 実装）に分け、境界違反は
  syn checker の port-adaptor 境界ルールで機械検査する。旧 fraktor-rs の
  port-adaptor-boundary-lint は内部で syn を使っていた実績があり、この段は
  ng の lint 方針と素直につながる。クレート数は増えない
- **段階2（クレート分割）**：旧 fraktor-rs と同じく core クレートと adaptor
  クレートに割る。no_std の保証がコンパイラで強制される最も強い形だが、
  クレート数はほぼ倍になる（案Cで約23→約46）。no_std が本当に要るクレート
  （actor 核が第一候補）だけに限定して適用するのが現実的
- **段階3（全面分割）**：全クレートを段階2にする。no_std ターゲット（組み込み等）
  が確定している場合にのみ正当化される

### 推奨の修正：案C＋段階1を既定とし、段階2は必要になったクレートだけ

- 既定は段階1。port の切り方（Clock、Scheduler、Random 等、プラットフォームに
  触れる面の列挙）は設計として先に固定し、境界は syn checker で守る
- no_std の要否自体は未決定のままでよい。要求が確定したクレートから段階2へ
  上げる。上げる対象はクレート単位で見えているので、移行は局所的
- 段階1の弱みは、強制がコンパイラではなく checker 依存になること。ただし ng は
  TAKT の機械検証に syn checker を組み込む前提（決定3）なので、運用上の穴は小さい

## 推奨

案C（写像ベースのハイブリッド）に、port & adapter の段階1を組み合わせた形を推す。
理由は、移植プロジェクトの監査可能性（台帳との対応）が最も効く局面で
案Aの長所を保ちながら、案Aの短所である「JVM 都合まで写す」部分だけをカテゴリ規則で
落とせるため。案Bは、対応表と構造ルールの維持コストを旧 fraktor-rs で実測済みであり、
正が Pekko のテストである以上、対応の単純さの価値が大きい。
port & adapter については、横の切り方とは独立に、依存方向の規律として全クレートに
かける。no_std のためのクレート分割は、要求が確定したクレートだけに限定する。
