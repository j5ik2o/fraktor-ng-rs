# 実装戦略グラフモデルの提案

状態: proposal（Fable 提案、未承認。承認は人間が行う）

作成日は 2026-11-11。承認されるまで設計設定ではない。

入力は `fable-input-fraktor-restart-v1.1.zip` の 6 ファイルである。同梱の `ledger.yaml` と `module-deps.dot` が `docs/baseline/pekko-v1.7.1/` の凍結物とバイト一致することを `cmp` で確認した。`05-decisions-and-spikes.md` の決定 1 から 3 は前提として扱い、再検討していない。

## 根拠の印

数字には出所の印を付ける。

- 【台帳】は、同梱の `ledger.yaml` と `module-deps.dot` から再計算した値である。
- 【再計測】は、Pekko v1.7.1 を clone し、台帳の 1,262 ファイルを正規表現で数え直した補足値である。baseline には入っていない。存在判定による近似であり、継承やヘルパ経由の利用は見えない。
- 【目視】は、Pekko v1.7.1 の該当ファイルで、宣言、ケース名、該当行を読んで確かめた事実である。ファイル全体を精読したわけではない。
- 【推定】は、上の 3 つからの推論である。確かめていない。

【台帳】と【再計測】は次のコマンドで再現できる。

```sh
python3 ledger/tools/recount_supplement.py --baseline <ledger.yaml か JSON> --pekko <Pekko v1.7.1 の checkout>
```

## 要点

1. ノードはテストクラスファイル 1 件とする。提案デフォルトを採るが、ID をファイルパス由来に変える。`<module>:<class>` は 31 件が衝突する【台帳】。
2. 辺は 3 種とする。スケジューラが強制するのはゴール間の `requires` と `write_scope` だけにする。ノード間の辺は、その 2 つを決めるための根拠に留める。
3. ゴールは明示列挙したノード集合とする。完了条件は「全ノードが green か do_not_port、かつ退行なし」である。
4. 最初の縦切りは 3 つの連続ゴールで、8 ノード、約 41 ケースである。2 つ目のゴールを出す前に、実行基盤の決定が要る。
5. 主指標はクラス数ベースの合格率とする。台帳のケース数は `taggedAs` つきの 314 ケースを数えていない【再計測】。分母には使えない。

## 1. ノード粒度

### 提案

ノードは Pekko のテストクラスファイル 1 件とする。提案デフォルトのテストクラス粒度を採る。そのうえで 3 点を足す。

**ID はファイルパスから作る。** ノードの一意キーは Pekko リポジトリ相対のファイルパスとする。`<module>:<class>` は表示名として残す。

**ノードに種別を持たせる。** 種別は `test`（既定）と `fixture` の 2 つである。`fixture` はテストケースを持たない基底クラスやヘルパを指す。例は `testkit` の `PekkoSpec` である。`fixture` は合格率の分母に入れない。種別を `fixture` に変える操作は分母を変えるので、do_not_port と同じく人間の承認を要する。

**ケース単位の勘定をノードの属性として持つ。** ノードは分割しない。Rust へ移植した時点で、移植済みケース数、通過ケース数、除外したケースの名前と理由を記録する。数は Rust 側のテスト実行結果から取る。ケース単位の除外は do_not_port の細粒度版なので、決めるのは人間だけとする。

モジュールとゴールはノードにしない。モジュールは集計キーであり、ゴールはノードの部分集合である。

ノード集合は台帳の 1,262 ファイルである。次の 2 つは集合の外にある【台帳】。

- `src/multi-jvm` の 179 ファイル（8 モジュール）。
- ファイル名が Spec、Suite、Test、Tests で終わらないテスト。

スキーマの器は変換器側で決める前提なので、上の 3 点は器への要求として読んでほしい。

### 根拠

- `<module>:<class>` は一意でない。31 件の ID が衝突し、64 ファイルが巻き込まれる。29 件は同じ言語で別ディレクトリ、2 件は Java と Scala の同名である。ファイルパスは 1,262 件すべて一意である【台帳】。衝突の例は `remote` の `RemoteDeathWatchSpec`（`artery` と `classic`）と、`actor-typed-tests` の `ActorSystemSpec`（`typed` と `typed/internal`）である。
- ノードは 1 回の takt run に収まる大きさが大半である。ケース数の中央値は 3、90 パーセンタイルは 14、最大は 121 である。5 ケース以下が 837 件（66%）、21 ケース以上は 63 件である【台帳】。
- ファイルの実在は確かである。1,262 ファイルすべてが v1.7.1 に存在し、台帳のケース数は 1,262 件すべてで再現できた【再計測】。近似なのはケース数であって、ノードの同一性ではない。
- ケース数 0 のクラスが 184 件ある【台帳】。中身は混ざっている【再計測】。14 件は `taggedAs` つきのケースだけを持つ本物のテストで、合計 198 ケースある。13 件は abstract class か trait だけである。残り 157 件は、名前から読める範囲で compile-only、API 確認、性能計測、TCK を含む【推定】。台帳の 0 は分類ではないので、種別は triage で付ける。
- クラス単位の 4 状態だけでは表せない場合がある。`actor-tests` の `ActorRefSpec` は 12 ケースを持ち、3 ケースが Java 直列化を名指しで使う【目視】。ケース単位の除外が無いと、クラス全体を do_not_port にするか、永久に red のまま置くかの 2 択になる。Java 直列化の API を参照するファイルは 10 件、63 箇所ある【再計測】。

### 検討したが採らない案とその理由

| 案 | 採らない理由 |
|---|---|
| モジュールをノードにする | テストを持つモジュールは 32 個で、最大の `stream-tests` は 254 クラスある【台帳】。完了判定がほとんど真にならず、部分的な進捗を表せない。 |
| テストケースをノードにする | baseline はケースを名指しできない。ケース数は正規表現の近似で、`taggedAs` つきの 314 ケースを落としている【再計測】。ノード数は 7,500 を超え、人間がゴールを置けない。 |
| パッケージ単位のクラス群をノードにする | docs を除く（モジュール, パッケージ）区画は 151 個で、中央値は 2、最大は 179、1 クラスだけの区画が 50 個ある【台帳】。大きさが揃わない。群の切り方は知識が増えると変わるので、ID に焼き込むと作り直しになる。群はゴールで表す。 |
| 実装シンボルや機能をノードにする | テストから実装への対応は 292/1,262 しか取れていない【台帳】。機能の分類表を作ることになり、仕様の発明にあたる。 |

## 2. 辺の種類

### 提案

辺は 3 種とする。種類ごとに、着手順序への効き方と並行可能性への効き方を変える。

| 辺 | 向き | 出所と確度 | 着手順序への効果 | 並行可能性への効果 |
|---|---|---|---|---|
| 実装依存 `impl` | テストノードから実装モジュールへ | 所属モジュールの `dependsOn` の推移閉包。モジュール粒度では確かだが、スコープは未分離【台帳】 | ゴールが書き込まない上流モジュールは、`requires` で先行させる | 書き込む実装が重なるゴールは同時に走らせない |
| テスト基盤依存 `infra` | テストノードからテスト基盤へ | クラス単位の値は baseline に無い。存在判定なら機械抽出できる【再計測】 | unported から red への着手をゲートする | テスト基盤を書くゴールは同時に 1 本だけにする |
| 意味的依存 `semantic` | テストノードからテストノードへ | 台帳に無い。triage か人間が理由つきで付ける | ゴール内の優先度だけに使う。ゲートにしない | 効かせない |

`impl` の扱いを補足する。ノード単位では、どの上流が「そのテストで実装が入る場所」で、どれが「前提」かを区別できない。そこでゴールが `write_scope` を宣言し、閉包のうち `write_scope` に入らないモジュールを `requires` で覆う。`referenced_modules`（import 近似）は足し算のヒントとしてだけ使う。依存を消す根拠には使わない。

`infra` の行き先は 3 つに分ける。

- 能力。`TestProbe`、expectMsg 系、`EventFilter`、`TestLatch` など。
- 基底 fixture。`PekkoSpec`（340 ファイルが継承）、`StreamSpec`（186 ファイルが継承）、ActorTestKit 系（186 ファイルが参照）【再計測】。
- 他モジュールのテストソース。主ソースが 0 行のモジュールを依存先に持つ辺が 12 本ある【台帳】。例は `remote` から `actor-tests` への辺で、依存先に主ソースが無い以上、テストソースの再利用でしかない。

`infra` のゲートは 3 層までの粗さに留める。層の中身は 4 章に書く。能力 1 つずつの順序は付けない。

スケジューラが強制するのは、ゴール間の `requires` と `write_scope` の 2 つだけとする。ノード間の辺は近似なので、その 2 つを人間が決めるための根拠として扱う。規則は次のとおりである。

- ゴールは、`requires` に挙げたゴールがすべて完了したら着手できる。
- 2 つのゴールは、`write_scope` が重ならず、少なくとも一方が基盤ゴールでないときに同時実行できる。
- 同時に走るゴールは 2 本までとする。

### 根拠

- モジュール依存は 152 辺で循環が無い。最長経路で数えると 0 から 14 の 15 層になる【台帳】。ただしスコープが未分離なので、層の番号は目安である。152 辺のうち 12 本は主ソース 0 行のモジュールへ、38 本は testkit 系の 6 モジュールへ向かう【台帳】。
- import 近似はクラス間の順序付けに使えない。参照モジュールが取れたのは 223 クラス（17.7%）である。そのうち 222 クラスは、所属モジュールの依存閉包の中だけを指す【台帳】。モジュール依存に無い情報をほとんど足さない。唯一の例外は `actor-tests` の `LoggingAdapterTest` が `stream` を指す件で、実際の import はテスト側の型 `event.ActorWithMDC.Log` である【目視】。誤解決である。
- テスト基盤は少数で、ほぼ全ノードが共有する。`testkit` に推移的に依存するモジュールは 32 個で、そこに 1,244 テストクラス（98.6%）がある【台帳】。順序の制約として最も効く。
- `infra` を red のゲートにする理由は、移植したテストが Rust 側の TestKit API に対して書かれるからである。API が無い時点で移植すると、推測した API が移植テストに焼き込まれる。
- `semantic` をゲートにしない理由は、事実層に根拠が無いからである。ゲートにすると、順序を発明することになる。

### 検討したが採らない案とその理由

| 案 | 採らない理由 |
|---|---|
| import 近似でクラス間の順序を作る | 覆うのは 17.7% で、その 99.6% はモジュール依存と重複する【台帳】。import が無いことは依存が無いことを意味しない。 |
| 辺を `depends_on` の 1 種に畳む | `impl` は自モジュールのテストの red を止めないが、`infra` は止める。1 種に畳むとこの差を表せない。 |
| `infra` を green のゲートだけに使い、red は先にすべて書く | 存在しない TestKit API に対する移植が溜まり、API が決まるたびに書き直しになる。 |
| `semantic` を機械抽出する | 抽出元になる事実が無い。 |
| モジュール層の番号をそのまま優先度に使う | 層の番号は test スコープの辺に左右される。スコープを分離するまで、番号に意味を持たせない。 |

## 3. ゴールの切り方

### 提案

ゴールは、明示列挙したノード集合に `requires`、`write_scope`、完了条件を付けたものとする。

```yaml
goal:
  id: G0b
  title: TestKit の種と actor 最小核
  kind: foundation        # foundation か port
  nodes:                  # 明示列挙する。発行後の増減は人間だけが行う
    - testkit/src/test/scala/org/apache/pekko/testkit/PekkoSpec.scala          # fixture
    - testkit/src/test/scala/org/apache/pekko/testkit/ImplicitSenderSpec.scala
    - testkit/src/test/scala/org/apache/pekko/testkit/DefaultTimeoutSpec.scala
    - testkit/src/test/scala/org/apache/pekko/testkit/TestActorsSpec.scala
  requires: [G0a]         # すべて done になるまで着手しない
  write_scope:            # 実行中の他ゴールと重なってはならない
    - {pekko_module: testkit, package: testkit}
    - {pekko_module: actor, package: actor}
  provider: cloud
```

完了条件は 2 段で、どちらも台帳の状態だけで判定する。

- `ported` は、全ノードが red、green、do_not_port のいずれかになった状態である。
- `done` は、全ノードが green か do_not_port になり、かつ退行が無い状態である。退行が無いとは、ゴール開始時に green だったノードが、判定時にも green であることを指す。

`fixture` ノードは「移植済み」をもって green と同じに扱う。全ノードが do_not_port になったゴールは、完了だが合格率に寄与しないものとして閉じる。do_not_port への遷移は人間だけが行えるので、manager が除外で完了を作ることはできない。

ゴールの種別は 2 つとする。

- 基盤ゴール（`foundation`）は、テスト基盤と、複数の区画が共有する核を書く。同時に 1 本だけ走らせる。
- 移植ゴール（`port`）は、1 つの（モジュール, パッケージ）区画の中のノード群を扱う。

移植ゴールの `requires` には、ノードが使うテスト基盤の層（4 章）を完成させた基盤ゴールを入れる。`infra` のゲートは、この形でゴール間の `requires` に写る。

ゴールの大きさは 5 から 15 ノードを初期値とする。21 ケース以上のノードは 1 ノードで 1 ゴールにしてよい。この数字は実測に基づかない。最初の縦切りで 1 ノードあたりの所要時間を測り、見直す。

並行は次の形にする。

- 最初のゴール（4 章の G0a）が完了するまでは 1 本で走らせる。
- その後は 2 本にする。1 本目は基盤ゴールか核の移植ゴールを走らせる。2 本目は、TestKit も ActorSystem も使わないノード群を走らせる。`actor-tests` では 47 クラス、約 405 ケースがこれにあたり、26 クラスはパッケージ `util` にある【再計測】。

権限は次のように分ける。

| 操作 | 行える者 |
|---|---|
| unported から red、red から green への遷移 | takt run |
| green から red への遷移（回帰の検出） | 自動 |
| do_not_port への遷移と、その取り消し | 人間だけ |
| ケース単位の除外、種別を `fixture` に変えること | 人間だけ。run は候補と理由を出す |
| ゴールの `nodes`、`requires`、`write_scope` の変更 | 人間だけ |

manager に渡す文面には、禁止事項を 3 つ入れる。ノードを do_not_port にしないこと。`write_scope` の外を書かないこと。ゴール外のノードの状態を変えないこと。移植ゴールがテスト基盤の変更を必要としたら、止めて報告させる。人間が基盤ゴールを出す。

タスクの分解は manager の仕事だが、1 タスクを 1 ノードにすることを勧める。手順は、triage、移植、red の確認、実装、green、台帳の更新の順である。triage で出た do_not_port の候補は、そのゴールの最初の問い合わせとして人間に上がる。

provider は、基盤ゴールをクラウド、移植ゴールを DGX とする案を出す。基盤ゴールが決める API は最大 1,244 クラスの移植に波及する【台帳】。移植ゴールは件数が多く、型が決まった作業である。スループットの実測は無いので、この配分は【推定】である。

#### 前提分岐：クレート構成

`write_scope` は Rust 側の書き込み範囲を表す。クレート構成が未決定なので、上の例では Pekko 側の（モジュール, パッケージ）で書いた。

- **案 A（Pekko モジュール写像型）の場合。** `write_scope` は Pekko の（モジュール, パッケージ）から機械的に導ける。重なりの検査も機械化できる。
- **案 B（層型）の場合。** Pekko の（モジュール, パッケージ）から Rust のクレートとモジュールへの対応表が先に要る。対応表ができるまでは、Pekko の実装モジュール 1 つにつき同時 1 ゴールに制限する。

テストのパッケージを実装の書き込み範囲の代理に使うのは【推定】である。import 対応が取れない主因は、テストが対象コードと同じパッケージにあることだと summary が述べている。この主因が正しければ、テストのパッケージは実装のパッケージとおおむね一致する。

### 根拠

- 決定 2 は、ゴールを manager にそのまま渡せる単位とし、完了条件を台帳の状態遷移で機械判定できる形にすると定めている。明示列挙したノード集合は、この条件を最も単純に満たす。
- 決定 3 は、機械検証が軽く速く回る前提でゴールを設計してよいとしている。退行の検査（全 green ノードの再実行）をゴール完了のたびに回す設計は、この前提に立つ。テスト全体の実行時間そのものは測っていない。
- docs を除く 151 区画のうち 133 区画は 15 ノード以下である。残り 18 区画に 625 クラスが集まる【台帳】。15 ノード上限なら、ゴール数はおよそ 89 から 184 になる【台帳】。人間が 1 件ずつ置ける件数である。
- 実効並行は約 2 本である。初期の作業はほぼすべて `actor`（主ソース 61,130 行）に書き込むので、モジュール単位の排他では 2 本目が動かない。パッケージ単位に下げ、さらに TestKit を使わないノード群を 2 本目に回す。

### 検討したが採らない案とその理由

| 案 | 採らない理由 |
|---|---|
| モジュール 1 個を 1 ゴールにする | `stream-tests` は 254 クラス、`actor-tests` は 177 クラスある【台帳】。完了まで長く、途中の判定ができない。 |
| 「合格率が X% 以上」を完了条件にする | どのノードが残ったかが条件から読めない。難しいノードが残り続ける。 |
| 1 ノードを 1 ゴールにする | ゴールが 1,000 件を超える。人間の仕事である「ゴールを置く」が回らない。 |
| 機能テーマでゴールを切る（例は「supervision を実装する」） | 完了を台帳の状態で判定できない。機能の境界を発明することになる。 |
| 移植だけのゴールと実装だけのゴールに分ける | 同じテストファイルを 2 つのゴールが触る。red のままのテストが、動いている API の上に長く残る。 |
| 3 本以上の並行を前提に細かく割る | DGX の実効並行は約 2 本である。 |

## 4. 最初の縦切り

### 提案

最初の縦切りは 3 つの連続ゴールとし、1 本で走らせる。合計 8 ノード（テスト 7、fixture 1）、台帳のケース数で 41 である。

| ゴール | ノード（台帳のケース数） | 作らせるもの |
|---|---|---|
| G0a 台帳パイプラインの通し | `actor-tests` の `ActorPathSpec`（15）、`RelativeActorPathSpec`（4） | アクターパスの解析と整形。台帳の遷移、完了判定、ロールアップ |
| G0b TestKit の種と actor 最小核 | `testkit` の `PekkoSpec`（fixture）、`ImplicitSenderSpec`（1）、`DefaultTimeoutSpec`（1）、`TestActorsSpec`（2） | ActorSystem の起動と停止、Props、actorOf、送信と sender、testActor、expectMsg |
| G0c TestProbe と最初の利用側 | `testkit` の `TestProbeSpec`（16）、`actor-tests` の `ForwardActorSpec`（2） | TestProbe、expectNoMessage、ask、子アクターの生成と再起動、AutoPilot、watch |

G0a の 2 クラスは `AnyWordSpec with Matchers` を継承し、ActorSystem も TestKit も使わない【目視】。未決定事項のうち、G0a が触れるのはクレート構成だけである。

G0c が長引く場合は、TestProbe を使わないノードの移植ゴールを、G0b だけを `requires` にして先に出せる。

#### TestKit 基盤と actor 最小核の関係

TestKit 基盤と actor 最小核は、どちらも単独では green にできない。同じゴール列の中で一体で作る。

- Pekko では `testkit` が `actor` に依存する【台帳】。`actor` 自身はテストクラスを 1 件も持たない。`actor` を検証するテストは `actor-tests`（177 クラス）と `testkit`（15 クラス）にある【台帳】。したがって、actor 核の green を判定するテストは、G0a のような例外を除いて TestKit 越しにしか存在しない。
- 逆に、TestKit だけを先に作ることもできない。最小の `ImplicitSenderSpec` でさえ ActorSystem を作り、その上の testActor を参照する【目視】。
- 両者の間で最初に決まるのは「テストスレッドが、アクターの処理結果をどう待つか」である。`TestProbeSpec` の最初のケースは、probe へ ask した直後に `expectMsg(0.millis, "hello")` が通ることを要求する。コメントは、TestActor が CallingThreadDispatcher 上で動くからだと説明している【目視】。probe への送信は、送信した呼び出しの中で観測できなければならない。
- 決定 1 に照らすと、testActor は executor が所有するセルの 1 つである。テスト側が持つのは ActorRef のハンドルと、probe のキューの受信側になる。これは決定 1 が Arc を許す「スレッド境界の送信端」に近い場所である【推定】。最初の縦切りは、決定 1 を実際のテストで確かめる最初の機会になる。

#### テスト基盤の層

`infra` のゲートに使う層を、能力の存在判定で 3 つに分ける。`actor-tests` の 177 クラスの内訳は次のとおりである【再計測】。

| 層 | 能力 | `actor-tests` のクラス数（台帳のケース数） | 検証するノード（`testkit`） |
|---|---|---|---|
| なし | ActorSystem も TestKit も使わない | 47（405） | なし |
| 1 | `PekkoSpec`、testActor、`ImplicitSender`、expectMsg 系、`expectNoMessage`、`TestProbe`、`expectTerminated` | 64（377） | G0b と G0c のノード |
| 2 | 層 1 に加えて `EventFilter`、`TestLatch`、`within`、`awaitAssert`、`awaitCond`、`fishForMessage` など | 58（484） | `TestEventListenerSpec`（9）、`PekkoSpecSpec`（4）、`TestTimeSpec`（2） |
| 3 | 層 2 に加えて `TestActorRef`、`TestFSMRef`、`CallingThreadDispatcher`、`TestBarrier`、AutoPilot | 8（97） | `TestActorRefSpec`（23）、`TestFSMRefSpec`（6） |

`TestProbeSpec` は層 3 のトークンである `setAutoPilot` と `CallingThreadDispatcher` を含む【再計測】。それでも TestProbe の正なので G0c に入れる。

縦切りの次は、層 2 の基盤ゴールを勧める。lifecycle、DeathWatch、supervision のような核の挙動テストは層 2 を要する。パッケージ `actor` の 49 クラスのうち 26 クラスが層 2 である【再計測】。その先の順序は、ここでは付けない。

`testkit` の `CoronerSpec`（4）と `MetricsKitSpec`（5）は ActorSystem も TestKit も参照しない【再計測】。名前からは JVM 側の道具に見える【推定】。do_not_port にするかどうかの判断材料として挙げる。

#### 前提分岐：実行基盤

ノード集合は分岐しない。分かれるのは、probe が結果を待つ方法である。

- **独自スケジューラの場合。** テストスレッドが executor を駆動して待つ形を取れる。時間に依存するテストを仮想時間で動かす余地がある。
- **tokio に載せる場合。** probe はチャネルの受信をタイムアウトつきで待つ。テストの実行形態は tokio のランタイムに合わせる。

どちらでも、G0b を出す前に実行基盤の決定か暫定方針が要る。G0a は実行基盤に依存しないので、先に出せる。

#### 前提分岐：typed と untyped の順序

上の表は untyped を先行させる場合の具体化である。typed を正とする場合、G0a は同じで、G0b と G0c を次に差し替える。

| ゴール | ノード（台帳のケース数） |
|---|---|
| G0b-T | `actor-testkit-typed` の `ActorTestKitSpec`（19）、scaladsl の `TestProbeSpec`（13） |
| G0c-T | `actor-typed-tests` の `StopSpec`（5）、`MonitorSpec`（3）、`GracefulStopSpec`（2）、`ReceivePartialSpec`（2）、`OnSignalSpec`（1） |

G0a が同じになるのは、typed の `ActorRef` が `def path: classic.ActorPath` を持つからである【目視】。G0c-T の 5 クラスは、ActorTestKit、TestProbe、LogCapturing だけを参照する小さなクラスから選んだ【再計測】。同じ条件を満たすクラスは `actor-typed-tests` に 41 個ある【再計測】。`ActorTestKitSpec` は classic の adapter を 2 箇所で import する【目視】。typed を classic の上に載せない構成を選ぶ場合、該当するケースの扱いを triage で決める必要がある。

typed の分岐には注意が 1 つある。TestKit 頻度の表は typed の probe API を測っていない。`actor-testkit-typed` は TestProbe が 54 回出るのに expectMsg は 0 回である【台帳】。typed の probe は `expectMessage` 系（155 ファイル、1,745 箇所）と `receiveMessage` 系（131 ファイル、736 箇所）を使う【再計測】。「expectMsg 系が最優先」は classic の API についての結論である。

#### 前提分岐：no_std

ノード集合は分岐しない。no_std を要求する場合は、TestKit を std 専用にするかどうかを G0b の前に決める必要がある。要求しない場合、この論点は生じない。

### 根拠

- TestKit 頻度は expectMsg 系が 3,954 回、TestProbe が 1,756 回で最上位である【台帳】。G0b と G0c は、この 2 つを Pekko 自身のテストで検証する最小のノード集合である。
- `PekkoSpec` を継承するファイルは 340 件あり、`actor-tests` では 177 件中 114 件である【再計測】。`PekkoSpec` は `testkit` のテストソースにある abstract class で、ケースを持たない【目視】。fixture として最初に要る。
- 最初の縦切りには、未知が 3 つ重なる。工場のパイプライン、TestKit と executor の待ち方、新しい所有権モデル上の actor 核である。G0a は 1 つ目だけを先に確かめる。2 ノードで済む。
- G0a のノードは捨て作業にならない。アクターパスは ActorRef と ActorSelection の前提である【推定】。

### 検討したが採らない案とその理由

| 案 | 採らない理由 |
|---|---|
| `testkit` の 15 クラスをすべて先に green にする | 層 3 の `TestActorRef` は 9 ファイル、87 箇所でしか使われない【再計測】。`TestActorRefSpec` と `TestFSMRefSpec` は FSM や dispatcher の差し替えを要する。 |
| `actor-tests` の核の挙動（lifecycle、DeathWatch、supervision）から始める | 読んだ 8 クラスのうち 7 クラスが `EventFilter` を使う【目視】。層 2 が先に要る。 |
| 頻度上位の API だけを薄く作り、`testkit` のテストを通さずに先へ進む | 正は Pekko のテストである。TestKit の誤りは、下流の全ノードの red と green の判定を汚す。 |
| `actor-tests` を丸ごと最初の縦切りにする | 177 クラスあり、層 3 まで要る。 |
| `util`（ByteString など）を最初の縦切りにする | TestKit も executor も通らないので縦切りにならない。2 本目の並行に回す。 |
| `TestProbeSpec` を G0b に入れる | ask、子アクターの再起動、AutoPilot を要する【目視】。最初の green が遠くなる。 |

## 5. ロールアップ

### 提案

集計はすべて台帳から計算する。台帳には保存しない。任意のノード集合 S（モジュール、ゴール、全体）について、次のように定義する。

| 記号 | 定義 |
|---|---|
| N | S のうち種別が `test` のノード数 |
| G、R、U、X | N のうち green、red、unported、do_not_port の数 |
| 対象数 D | N − X |
| 合格率 | G ÷ D。D が 0 なら「対象なし」と表示する |
| 着手率 | (R + G) ÷ D |
| 除外率 | X ÷ N。合格率と必ず並べて出す |

- **モジュール合格率**は、S を台帳の所属モジュールのノードとした合格率である。
- **全体進捗**は、S を全ノードとした合格率である。モジュール合格率の平均は取らない。
- **ゴールの進捗**は、ゴール内で green か do_not_port のノード数を、ゴールのノード数で割った値である。1 になり、退行が無ければ `done` である。
- `fixture` は N に入れない。「fixture 移植済み k 件中 m 件」として別に出す。
- 表示は割合だけにしない。G、R、U、X の件数と、triage が未了の件数を必ず添える。

補助指標として通過ケース数を出す。Rust 側のテスト実行で通ったケースの合計で、絶対数として表示する。完了条件には使わない。参考の分母を添えるなら「7,561 以上」と書く。

主ソースを持つが自分のテストを持たないモジュールがある。たとえば `actor`、`actor-typed`、`stream` である【台帳】。モジュール合格率は所属モジュール（`actor-tests` など）で出す。`actor-tests` を `actor` に読み替える族ビューは、対応表を人間が承認してから足す。

状態遷移の条件は次のとおりである。

| 遷移 | 条件 |
|---|---|
| unported から red | Rust のテストファイルを台帳に登録し、実行して 1 件以上が失敗した |
| red から green | 移植したケースがすべて通り、かつ Pekko 側の全ケースが「移植済み」か「人間が承認した除外」のどちらかに入った |
| green から red | 全体の再実行で失敗した |
| do_not_port への遷移 | 人間が理由を記入した |

最初の縦切りが終わった時点の期待値を書いておく。集計の実装を確かめる検算に使える。untyped を先行させ、do_not_port が 0 件で、`fixture` が `PekkoSpec` の 1 件だけなら、`testkit` は 4 ÷ 14 で 28.6%、`actor-tests` は 3 ÷ 177 で 1.7%、全体は 7 ÷ 1,261 で 0.56% になる。

do_not_port の判断材料として、`docs` の数字を挙げる。173 クラス、577 ケース、ケース数 0 が 40 件、直接依存が 22 モジュールで、依存の最下流にある【台帳】。人間が決めるまで、`docs` は unported として分母に残る。

### 根拠

- クラス数は確かで、ケース数は近似である。台帳のケース数は `taggedAs` つきのケースを数えていない。該当は 35 ファイル、314 ケースで、`actor-tests` だけで 152 ケースある【再計測】。`actor-tests` の `FSMTimingSpec` は 10 ケースすべてがタグつきで、台帳では 0 である【目視】。
- この過小評価は偏っている。タグは時間依存や長時間のテストに付く。ケース数で重み付けすると、最も難しい種類のテストが軽く数えられる。
- モジュールの大きさは 1 クラスから 254 クラスまで開く【台帳】。モジュール合格率の平均を全体進捗にすると、`osgi`（1 クラス）と `stream-tests`（254 クラス）が同じ重みになる。
- do_not_port を分母から外すと、除外を増やすだけで合格率が上がる。除外率を並べて出せば、その動きが見える。
- 台帳スキーマの叩き台は、集計値を台帳に二重に持たないと定めている。この提案はそれに従う。

### 検討したが採らない案とその理由

| 案 | 採らない理由 |
|---|---|
| ケース数で重み付けした合格率を主指標にする | 分母が近似で、偏って過小である。 |
| モジュール合格率の単純平均を全体進捗にする | 小さいモジュールが全体を動かす。 |
| do_not_port を green と同じに数える | 何も移植していないのに進捗が上がる。 |
| do_not_port を分母に残す | 100% に届かなくなる。「やらない」と「まだ」が混ざる。 |
| red に部分点を与える | 重みの根拠が無い。着手率を別に出せば足りる。 |
| テスト行数で重み付けする | テスト行数はモジュール単位でしか台帳に無い。 |

## 6. リスクと未確定事項

未決定事項への依存を先に挙げる。

| 未決定事項 | この提案が依存する箇所 | 影響 |
|---|---|---|
| 実行基盤 | G0b 以降 | G0b を出す前に、決定か暫定方針が要る。G0a は依存しない |
| typed と untyped の順序 | G0b と G0c のノード集合 | 4 章の分岐どおりに差し替わる |
| クレート構成 | `write_scope` の表現、G0a の置き場所 | 案 B では対応表が先に要る |
| no_std | TestKit の置き場所 | 要求する場合だけ、G0b の前に判断が要る |
| 設定体系の再現範囲 | `PekkoSpec` の移植 | `PekkoSpec` は `ConfigFactory` を使う【目視】。fixture の移植で最初に当たる |

事実層と設計のリスクを挙げる。

1. **ケース数の計上漏れ。** `taggedAs` つきの 314 ケースが台帳に無い【再計測】。baseline を作り直すときに、抽出の正規表現へ `taggedAs` を足すことを勧める。この提案はケース数を完了条件に使わないので、設計は影響を受けない。
2. **TestKit 能力の一覧の不足。** 台帳の 11 項目に無い能力が広く使われている【再計測】。`EventFilter` 系は 116 ファイルで 471 箇所、`testActor` は 157 ファイルで 805 箇所、`expectTerminated` は 130 ファイルで 348 箇所である。stream の testkit（`TestSubscriber` など）は 194 ファイルで 1,996 箇所ある。クラス単位の再抽出では、能力の一覧を広げる必要がある。
3. **層の分類は存在判定である。** 継承やヘルパ経由の利用は見えない。ケース単位でもない。層が「なし」のクラスが実際には ActorSystem を使う可能性が残る。triage で確かめる。
4. **`dependsOn` のスコープが未分離である。** 層の番号と、`impl` の閉包の広さに影響する。スコープを分離すれば、`requires` を狭められる。
5. **ノード集合の外にあるテスト。** multi-jvm の 179 ファイルは集計に入らない【台帳】。`cluster` 系のモジュール合格率は、multi-jvm を含まない値になる。全体進捗が 100% でも、Pekko の全テストを移植したことにはならない。
6. **red の機械判定。** Rust では、移植したテストがコンパイルできないと、同じテストターゲットのほかのテストも実行できない。1 ノードのコンパイルエラーが他ノードの判定を巻き込まない構成が要る。構成の取り方はクレート構成に依存する。
7. **初回から通るテスト。** 実装が先に存在するノードは、移植した時点で通る。red を確認できない。unported から green への直行を許すなら、その件数を別に数えて人間が見られるようにする必要がある。
8. **時間に依存するテスト。** `Thread.sleep` は 295 回、`eventually` は 108 回出る【台帳】。リポジトリ全体の Scala ソースでは、タグは `TimingTest` が 279 回、`LongRunningTest` が 192 回出る【再計測】。読み替えの方針は実行基盤が決まるまで決められない。
9. **ケース単位の除外による判断負荷。** Java 直列化を参照するファイルは 10 件である【再計測】。JVM 固有のケースはこれより多いはずである【推定】。除外の候補が増えると、人間の問い合わせ対応が詰まる。
10. **`TestActorRef` と所有権モデル。** `TestActorRef` は層 3 に置いた。`TestActorRef` は `underlyingActor` でアクター本体を返す【目視】。executor がアクター本体を単独所有する決定 1 の下で、この API をどう表すかは、層 3 の基盤ゴールを出す前に検討が要る。
11. **実測の無い初期値。** ゴールの大きさ（5 から 15 ノード）と provider の配分は、TAKT のスループットを測らずに置いた。最初の縦切りの実測で見直す。
12. **`semantic` の運用が未定義である。** 誰がいつ付けるかを決めていない。優先度にしか使わないので、空のままでも設計は成立する。

この提案の検証範囲を書いておく。引用した【台帳】と【再計測】の数字は `ledger/tools/recount_supplement.py` の出力と突き合わせた。【目視】は Pekko v1.7.1 の 20 ファイルを対象にした。独立したレビューは受けていない。TAKT 上での試行もしていない。

## 承認論点リスト

各項目は Yes か No で答えられる。

1. ノードを Pekko のテストクラスファイル 1 件とするか。
2. ノードの一意キーを `<module>:<class>` からファイルパスに変えるか。
3. ノードに種別（`test` と `fixture`）を持たせ、`fixture` を合格率の分母から外すか。

6. スケジューラが強制するものを、ゴール間の `requires` と `write_scope` の 2 つに限るか。
7. `infra` を、unported から red への着手のゲートにするか。
8. import 近似（`referenced_modules`）を順序付けに使わず、ヒントに留めるか。
9. ゴールを明示列挙したノード集合とし、完了条件を「全ノードが green か do_not_port、かつ退行なし」とするか。
10. 基盤ゴールを同時 1 本、全体を同時 2 本までとするか。
11. ゴールの大きさの初期値を 5 から 15 ノードとし、最初の縦切りの実測で見直すか。
12. 最初の縦切りを G0a、G0b、G0c の 3 ゴール（8 ノード）とするか。
13. TestKit を使わない 2 クラスの G0a を、縦切りの先頭に置くか。
14. G0b を出す前に、実行基盤を決めるか、暫定方針を置くか。
15. G0a の完了後に、TestKit を使わないノード群で 2 本目の並行を始めるか。
16. 主指標を、クラス数ベースの合格率 G ÷ (N − X) とし、除外率を並べて出すか。
17. 全体進捗を、モジュール合格率の平均ではなく全ノードの合算で出すか。

19. 基盤ゴールをクラウド、移植ゴールを DGX に割り当てるか。
20. `docs` の 173 クラスを do_not_port にするか。判断材料は 5 章にある。この項目に提案は付けていない。
