# Pekko 厳密分析：ツールと手順（Fable へのインプット）

目的：fraktor-rs 再実装の「実装戦略グラフモデル」の**事実層**を作る。
Pekko のコードを機械的・再実行可能に分析し、台帳とグラフの素材を生成する。
グラフの判断層（粒度・ゴール分割・順序ポリシー）の設計は、この分析結果を前提に別途行う。

## 前提として先に決めること

- **基準タグの固定**：移植対象とする Pekko のバージョン（タグ）を1つ決める。ここがずれると台帳全体がずれる
- **対象範囲**：全モジュールか、コア（actor / testkit 等）から始めるか

## ツール

| ツール | 役割 | 得られるもの |
|---|---|---|
| sbt（+ sbt-dependency-graph） | モジュール構造の抽出 | プロジェクト一覧、モジュール依存グラフ（宣言どおりで正確） |
| SemanticDB（scalac プラグイン） | 意味情報の生成 | 定義・参照・型をコンパイラ精度で記録したデータ。参照解析の土台 |
| SCIP + scip-java | 参照グラフ化 | SemanticDB から SCIP インデックスを生成し、シンボル単位の定義／参照関係を機械的に走査可能にする。sbt 対応。自動インデックスは Scala 2.13 のみ（Pekko 主軸は 2.13 なので可。Scala 3 側は SemanticDB を直接読む） |
| Scalafix（自作ルール） | 意味を伴う抽出 | SemanticDB 上でルールを実行。「賢い grep」の置き換え。抽出ロジック自体が再実行可能な資産になる |
| sbt テスト探索 + ソース走査 | テストの棚卸し | テストクラス一覧、テスト件数、規模 |

※ REA（morluto/rea）のようなリバースエンジニアリング系は使わない。ソースがない対象向けであり、今回はソースがあり決定論的抽出が要るため方向が逆。

## 手順

1. **基準タグで取得とビルド**：固定したタグで Pekko を clone し、SemanticDB 生成を有効化してコンパイル（テストコード側も対象にする）
2. **モジュール依存の抽出**：sbt からプロジェクト一覧と依存関係を出力し、モジュール依存グラフを作る
3. **テストの棚卸し**：モジュールごとにテストクラス・テスト件数・行数を集計する
4. **参照グラフの抽出**：SCIP インデックスから「テストクラス → 参照する実装シンボル」を引き、テストと実装の対応表を作る
5. **TestKit 使用実態の集計**：Scalafix ルール／走査で、どのテストがどの TestKit 機能（TestProbe、expectMsg 系、ラッチ等）を使うかを数える。TestKit 基盤の実装優先度はこの頻度で決まる
6. **前提フラグの検出**：時間依存、スレッド前提、ランダム性など、移植時に読み替えが要るテストに印を付ける（triage の下ごしらえ）
7. **台帳への整形**：抽出結果を台帳（YAML/JSON）に落とす。分析はスクリプト化し、基準タグを変えたら再生成できる状態にする
8. **グラフビューの生成**：台帳から DOT を生成し、依存と進捗を図で確認できるようにする（正は台帳、グラフはビュー）

## 台帳のノード（案）

- モジュール
- テストクラス（所属モジュール、テスト件数、規模）
- 参照する実装シンボル／モジュール（実装依存）
- 必要な TestKit 機能（テスト基盤依存）
- 前提フラグ（時間依存など）
- 状態（未移植 / 移植済み red / green / 移植しない）← 実行フェーズで更新

## この分析で取れないもの（判断層として Fable／人間が担う）

- 順序保証など実行時意味論の強さ、テストの意図
- 「移植しない」の最終判断（理由は台帳に記録する）
- ノード粒度、ゴールへの切り方、実行順序ポリシー、合格率のロールアップ定義
