# Fable への依頼メモ：fraktor-rs 再実装の実装戦略グラフモデル設計

## 背景

- fraktor-rs（Pekko の Rust 移植）を、Pekko のテストスイートを「正」として最初から再実装する
- 現行 fraktor-rs は仕様文書先行で進め、未検証の既存コードと文書が事実上のハーネス化してトークン効率が悪い。これを反転させる
- 工場の構成は TAKT 前提：director（常駐・監督）→ manager（リポジトリ単位のゴール担当）→ takt run（タスク実行ライン）。ゴールはモジュール境界でコンフリクトしないよう切る

## 同梱物（事実層：確定事項として扱うこと）

- `pekko-analysis-brief.md` — 分析のツールと手順、事実層／判断層の切り分け
- `summary.md` — Pekko 分析サマリ（基準タグ v1.7.1、39 モジュール、依存 152 辺、テストクラス 1,262、テスト件数 約7,561＝近似）
- `ledger.yaml` — モジュール → {依存先, ソース/テスト統計, テストクラス一覧, TestKit 使用, 前提フラグ} の台帳
- `module-deps.dot` — モジュール依存グラフ

## 事実層の既知の限界（前提として織り込むこと）

- テスト → 実装の対応は import ベースの近似で、カバー率は 292/1,262 に留まる（同一パッケージ参照とワイルドカード import が主因）。SemanticDB/SCIP による厳密化は未実施で、次段の作業として残っている
- テスト件数は正規表現カウントによる近似
- docs モジュールのテストクラス（173）はドキュメント用コードを含むため、移植対象として区別が必要

## 依頼範囲（判断層：ここだけを設計してほしい）

1. **ノード粒度**：グラフモデルのノードを何にするか（モジュール／テストクラス／テストクラス群）。ゴール＝ノードの部分集合になる
2. **辺の種類の定義**：実装依存、テスト基盤依存（TestKit 機能）、意味的依存をどう区別し、それぞれスケジューリングにどう効かせるか
3. **ゴールの切り方**：manager へ渡すゴールの分割ポリシー（コンフリクト回避、DGX の実効並行 約2本という制約、クラウド／DGX の provider 配分を含む）
4. **最初の縦切り**：TestKit 基盤＋最初のテスト群をどのモジュールで切るか（TestKit 頻度：expectMsg 系と TestProbe が最優先という数字を前提に）
5. **状態のロールアップ**：ノード状態（未移植 / red / green / 移植しない）をモジュール合格率と全体進捗にどう畳むか。manager のゴール完了条件をグラフ上で定義できる形に

## 依頼しないこと

- 構造の推論（モジュール依存・テスト棚卸し等の事実は同梱の台帳が正）
- 移植しない項目の最終判断（候補と理由の提示まで）
