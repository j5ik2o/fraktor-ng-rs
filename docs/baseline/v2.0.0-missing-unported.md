出す。この文書は、その 23 件を原典で 1 ノードずつ確かめた記録である（Orca 項目 258 の ②）。

## 確かめ方

### 23 件すべてに共通

1. `pekko/<id>` にファイルが無いこと（`check-ledger --pekko pekko`）
2. クラス名が v2.0.0 のソースに 1 件も無いこと
   （`git -C pekko grep -l -E '(class|object) <名前>' v2.0.0 -- '*.scala' '*.java'`）
3. v1.7.1 の版から取った代表的なケース名を v2.0.0 全体から検索し、当たったファイルが
   **v1.7.1 の時点でも同じケース名を持っていたか**を確かめる（持っていれば、移動先ではなく
   もとからの重複である）
4. v2.0.0 のツリーで同じファイル名のパスを探す（`git -C pekko ls-tree -r --name-only v2.0.0`）。
   この検索は**移動先の候補**を探すもので、当たった場合は 5 か 6 で移動先かどうかを決める

### 原典で削除（14 件）にだけ適用

5. そのパスを最後に触った commit が削除であること
   （`git -C pekko log -1 --format='%h %ad %s' --date=short v2.0.0 -- <id>` と、同じ引数に
   `--diff-filter=D` を付けた結果が一致する）。4 の検索で見つかった同じファイル名のパスは、
   v1.7.1 の時点から別に存在するスイートであることを 3 で確かめる（移動先ではない）

### 移動（9 件）にだけ適用

6. 移動先を決める。4 の検索で当たったパス、または v1.7.1 の版のケース名が v2.0.0 で入っている
   ファイルである。同じ commit の中の改名かどうかは `git -C pekko diff -M40% --name-status
   v1.7.1 v2.0.0 -- <旧パス> <移動先>` で確かめ、内容も比べる
7. 移動先が v2.0.0 の履歴に無い場合は、**そのパスが v2.0.0 の履歴に一度も現れない**ことを
   確かめる（`git -C pekko log -1 --format='%h %ad %s' v2.0.0 -- <id>` が空）。削除 commit は
   無い。当てはまるのは `actor-typed-tests` の `ActorSystemScala213PlusSpec` の 1 件で、
   これは 1.x の側で足されたファイルである

この clone では v1.7.1 のタグが 1 個の commit（履歴を持たない）で、v2.0.0 とは共通の祖先が無い。
そのため「削除した commit」は、v2.0.0 の履歴のうちにそのパスを削除した commit を指す。
移動は git の改名検出（`git diff -M`）と内容の比較で判定し、履歴の親子関係では判定していない。

### 前回の観測（移動 7・消失 16）との違い

前回はファイル名の一致で 7 件を移動としていた。原典を開いて確かめた結果、**移動 9・削除 14** に
変わる。理由は 3 つである。

- `ActorTestKitJUnit5Test` は、ファイル名が変わる改名（`ActorTestKitJUnitJupiterTest`）だった。
  ファイル名の一致では見つからないので、前回は消失に数えていた
- `JUnit5IntegrationExampleTest` も、`JUnitJupiterIntegrationExampleTest` への実質の置き換えだった
  （内容はほぼ同じで、名前の言い換えだけ）。同じく前回は消失に数えていた
- `remote/.../serialization/PrimitivesSerializationSpec` は、actor-tests 側の同名ファイルと
  ファイル名が一致するが、**移動先ではない**。actor-tests 側は v1.7.1 の時点から別に存在し、
  remote 側は非推奨コードの撤去（#1983）で消えた。前回は移動に数えていた

## 台帳に記録する形式が規定されていない（この作業で台帳を変えていない）

23 件はすべて `unported` で、`cases.ported` も `rust.test_file` も無い。台帳の既存の記録形式のうち、
「原典にファイルが無い」を表せるのは最上位の `retired`（退役）だけである。しかし `retired` は
`ledger/tools/lineage.py` が次を要求する。

- `retired.successor` が現行のノードの `id` であること
- その後継の `cases.carried` に、`from`・`source`・**`rust_test`**・`verified_against`・`evidence` を
  そろえた要素があること
- 後継が部分移植なら `ported = passing = 引き継いだ件数`、`total > ported`

移植 0 件のノードには `rust_test` と `evidence`（確かめた実行）が無く、後継の件数も作れない。
埋めれば記録の捏造になる。`triage.reason` も、スキーマの規則では `do_not_port` と `not_built` の
ときに人間が書く欄で、`unported` のノードに書いた前例は台帳に無い（`unported`・`red` で
`triage.reason` を持つノードは 0 件）。したがって、23 件を台帳へ記録する形式は**規定が無い**と
判断し、台帳は変えずにこの文書へ根拠を残した。

## 判断待ち（status・id の扱いを決める必要があるもの）

1. **原典で削除の 14 件**：移植対象が原典に無いので、`unported` のままでは green にならない。
   `do_not_port`（理由「原典 v2.0.0 で削除」）へ倒すか、退役として扱うか、`unported` のまま
   残すかを決める必要がある。残す場合、rollup の分母（N）に 14 件が残り続ける
2. **移動 8 件**：台帳の `id` は Pekko 相対のファイルパスで、これが一意キーである。移動先のパスへ
   `id` を付け替える（同じノードとして扱う）か、元の `id` を退役させて移動先に新しいノードを作るかを
   決める必要がある。付け替えると一意キーが変わるため、`docs/goals/` のゴール文書や `goal` の
   タグ付けとの対応も変わる
3. **移動（ケースのみ）の 1 件**（`actor-typed-tests` の `ActorSystemScala213PlusSpec`）：
   ケースは `ActorSystemSpec`（`unported`）へ移った。actor-tests 側の同じ経緯のノードは
   `retired` ＋ `cases.carried` で記録済みだが、こちらは移植 0 件なので同じ形が使えない
   （上記の `rust_test` と `evidence`）。この 1 件は、後継のケースを移植した時点で
   actor-tests と同じ形で記録できる
4. **形式そのもの**：`retired` に「後継なし・ケース引き継ぎなし」の退役（原典で削除）を許すか、
   ノードに「原典で削除」を持つ欄を足すか。台帳のスキーマ（`docs/decisions/ledger-schema-draft.md`）
   の決定として扱う
