## 確かめ方

### 23 件すべてに共通

1. `pekko/<id>` にファイルが無いこと（`check-ledger --pekko pekko`）
2. クラス名が v2.0.0 のソースに 1 件も無いこと
   （`git -C pekko grep -l -E '(class|object) <名前>' v2.0.0 -- '*.scala' '*.java'`）
3. v1.7.1 の版から取った代表的なケース名を v2.0.0 全体から検索し、当たったファイルが
   **v1.7.1 の時点でも同じケース名を持っていたか**を確かめる（持っていれば、移動先ではなく
   もとからの重複である）
4. v2.0.0 のツリーで同じファイル名のパスを探す（`git -C pekko ls-tree -r --name-only v2.0.0`）。
   この検索は**移動先の候補**を探すもので、当たった場合は 5 か 6 で移動先かどうかを決める

### 原典で削除（14 件）にだけ適用

5. そのパスを最後に触った commit が削除であること
   （`git -C pekko log -1 --format='%h %ad %s' --date=short v2.0.0 -- <id>` と、同じ引数に
   `--diff-filter=D` を付けた結果が一致する）。4 の検索で見つかった同じファイル名のパスは、
   v1.7.1 の時点から別に存在するスイートであることを 3 で確かめる（移動先ではない）

### 移動（9 件）にだけ適用

6. 移動先を決める。4 の検索で当たったパス、または v1.7.1 の版のケース名が v2.0.0 で入っている
   ファイルである。同じ commit の中の改名かどうかは `git -C pekko diff -M40% --name-status
   v1.7.1 v2.0.0 -- <旧パス> <移動先>` で確かめ、内容も比べる
7. 移動先が v2.0.0 の履歴に無い場合は、**そのパスが v2.0.0 の履歴に一度も現れない**ことを
   確かめる（`git -C pekko log -1 --format='%h %ad %s' v2.0.0 -- <id>` が空）。削除 commit は
   無い。当てはまるのは `actor-typed-tests` の `ActorSystemScala213PlusSpec` の 1 件で、
   これは 1.x の側で足されたファイルである

この clone では v1.7.1 のタグが 1 個の commit（履歴を持たない）で、v2.0.0 とは共通の祖先が無い。
そのため「削除した commit」は、v2.0.0 の履歴のうちにそのパスを削除した commit を指す。
移動は git の改名検出（`git diff -M`）と内容の比較で判定し、履歴の親子関係では判定していない。

前回はファイル名の一致で 7 件を移動としていた。原典を開いて確かめた結果、**移動 9・削除 14** に
変わる。理由は 3 つである。

- `ActorTestKitJUnit5Test` は、ファイル名が変わる改名（`ActorTestKitJUnitJupiterTest`）だった。
  ファイル名の一致では見つからないので、前回は消失に数えていた
- `JUnit5IntegrationExampleTest` も、`JUnitJupiterIntegrationExampleTest` への実質の置き換えだった
  （内容はほぼ同じで、名前の言い換えだけ）。同じく前回は消失に数えていた
- `remote/.../serialization/PrimitivesSerializationSpec` は、actor-tests 側の同名ファイルと
  ファイル名が一致するが、**移動先ではない**。actor-tests 側は v1.7.1 の時点から別に存在し、
  remote 側は非推奨コードの撤去（#1983）で消えた。前回は移動に数えていた

## 決定と反映（2026-11-25、起動元の決定。両方とも案 A）

23 件の扱いは 2026-11-25 に起動元（元帥）が決めた。台帳に新しい欄・新しい `status` は足していない。

1. **原典で削除の 14 件は `do_not_port`**。`triage.kind: do_not_port`、`triage.reason` に
   「原典 v2.0.0 で削除（削除コミット <SHA>・確認日 2026-11-25）」、`verified_against: v2.0.0` を
   書く。`retired` は使わない。後継が無いので `retired.successor` と、後継の `cases.carried` が
   要求する `rust_test`・`evidence`（確かめた実行）を埋められず、埋めれば記録の捏造になる
   （語義からも外れる）。理由の例は `ledger/README.md` に足した
2. **移動（同一ファイル）の 8 件は `id` を付け替える**。v2.0.0 の新しいパスを `id` にし、
   `status`・件数（`pekko.test_cases_approx`）・`cases`・`goal` はそのまま持ち越す。パスから
   決まる `name` と `pekko.class` だけを新しいクラス名に合わせる（クラス名が変わる 2 件）。
   旧 id の文字列参照（ゴール文書の対象表、`ledger`、`docs`、`.takt`、`scripts`）も置き換えた。
   旧 id は根拠表と git の改名履歴に残す
3. **移動（ケースのみ）の 1 件**（`actor-typed-tests` の `ActorSystemScala213PlusSpec`）は、
   今回は扱わない。後継の `ActorSystemSpec` へケースを移植するときに、actor-tests 側の同じ経緯の
   ノードと同じ `retired` ＋ `cases.carried` の形で記録する

置換は手で書かず、根拠表を読む `ledger/tools/relocate_nodes.py` で行った（台帳の行は
`ledger/tools/ledger_lines.py` を通す）。`apply` は、対象ノードの外の行と、対象ノードの中の
書き換えてよい欄（`id`・`name`・`pekko.class`、または `status`・`triage`・`verified_against`）
以外が変われば、書き込まずに失敗する。`check` は根拠表と台帳の整合と、旧 id の文字列参照 0 件を
CI で見る。適用は冪等である。

## 再現手順

```sh
# 原典を用意し、現行の基準であることを確かめる
bash tools/pekko-source/prepare_pekko_source.sh
python3 ledger/tools/pekko_baseline.py source-tag           # => v2.0.0

# 原典にファイルが無いノード（処理後は 15 件。当時は 23 件）と、v2.0.0 で未照合のノード
uv run --with pyyaml python3 ledger/tools/pekko_baseline.py check-ledger \
  --ledger ledger/nodes.yaml --pekko pekko --list-unverified

# 1 ノードずつの根拠（例：移動の 1 件）。旧 id は根拠表から取る（docs に旧 id を書かない）
table=docs/baseline/v2.0.0-port-targets.tsv
new=actor-typed-tests/src/test/scala/org/apache/pekko/actor/typed/internal/adapter/PropsAdapterSpec.scala
old=$(awk -F'\t' -v n="$new" '$1=="move" && $3==n {print $2}' "$table")
git -C pekko log -1 --format='%h %ad %s' --date=short v2.0.0 -- "$old"
git -C pekko ls-tree -r --name-only v2.0.0 | grep '/PropsAdapterSpec.scala$'
git -C pekko diff -M40% --name-status v1.7.1 v2.0.0 -- "$old" "$new"

# 置換の再現（冪等）と、根拠表・台帳・参照の検査
python3 ledger/tools/relocate_nodes.py apply --dry-run
uv run --with pyyaml python3 ledger/tools/relocate_nodes.py check
```
