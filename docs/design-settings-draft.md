# fraktor-ng-rs 設計設定ドラフト

状態: 叩き台（2026-11-11、未 push）。決定済み前提と、提案デフォルト＋要決定事項を分けて書く。

## 0. 進め方の原則（2026-11-11 ユーザー指示）

- **実装は最後の最後**。当面の作業は設計・台帳・グラフモデル・判断の固定が中心で、
  本実装（main へ入るコード）は設計が固まるまで始めない。
- **スパイクは可**。ただしスパイクは設計判断を検証するための使い捨てであり、本実装ではない。
  - 目的（どの判断を検証するか）を先に1行で書く
  - 結果はコードではなく「判断メモ」として残す。スパイクコードは main に混ぜない
    （spikes/ 配下か別ブランチに隔離し、採用判断が済んだら捨てるか作り直す）
  - スパイクで動いたことは、設計が正しい証拠の一部にすぎない。本実装の開始条件にはならない
- **自律の範囲**（2026-11-11 ユーザー指示）：取り返しの付かない操作だけ人間の承認を要する。
  それ以外（調査、スパイク、ドラフト作成、通常の commit / push 等）は自律的に進めてよい。
  判断に迷ったら抱え込まず相談する。
- **実装の実行基盤は TAKT 前提**（2026-11-11 ユーザー指示）。本実装フェーズは
  TAKT の director / manager / run の構成で回す。設計はこの前提に合わせて行う。
  - director: 常駐し、全体を見渡して知らせる（実行はしない）
  - manager: リポジトリ／ワークスペース単位のゴール担当。ゴールをタスクに分解して回す
  - takt run: 1タスクを実行するライン（plan → implement → review → fix）
  - 人間の仕事は「コンフリクトしない粒度で manager にゴールを置く」「問い合わせに答える」
    「マージを承認する」の3つに集約する
  - したがってグラフモデルのゴールは、manager にそのまま渡せる単位で定義できなければならず、
    ゴールの完了条件は台帳の状態遷移で機械判定できる形にする
  - 並行度はリソース側の制約も受ける（単一の DGX Spark x4 vLLM では実効並行は約2本が目安、
    という前提が Fable 表紙メモにも入っている）

## 1. 決定済み前提（旧 fraktor-rs からの教訓）

- **正は Pekko のテストスイート**。仕様文書を先に書いて実装を合わせる方式は採らない。
  文書と実装を同じ側が書くと意味論のズレが静かに溜まる（旧 fraktor-rs の失敗）。
- **基準は Apache Pekko v1.7.1 に固定**（安定版 v1.x 系の最大。RC / マイルストーン除外）。
  基準タグがずれると台帳全体がずれるため、変更は明示的な判断としてのみ行う。
- **移植は red → green**。タスクは実装から始めず、対応する Pekko テストの Rust 移植を
  先に含み、赤を確認してから緑にする。
- **台帳が正、グラフはビュー**。進捗の正は台帳（YAML/JSON）であり、DOT 等のグラフは
  台帳から生成する。グラフを直接編集しない。
- **「移植しない」判断は人間が先に固定する**。エージェントの裁量にしない
  （例: JVM 前提のシリアライゼーション形式）。
- **旧 fraktor-rs のコードは参照実装**。従うべきハーネスではない。
  読むかどうかはタスク側が選ぶ。

## 2. 事実層（Pekko v1.7.1 実分析、2026-11-11）

- 39 モジュール、モジュール依存 152 辺、主ソース 474,887 行 / テスト 294,382 行
- テストクラス 1,262 件、テスト件数 約 7,561（正規表現カウントの近似）
- テストクラス上位: stream-tests 254、actor-tests 177、docs 173（移植対象として区別）、

- 既知の近似限界: テスト→実装対応は import 近似で 292 / 1,262 クラスしか取れていない。
  SemanticDB / SCIP による厳密化が次段の課題。

## 3. 提案デフォルト（要決定）

### 3.1 初期スコープ＝縦切り1本

- Phase 0: TestKit 基盤（TestProbe + expectMsg 系）＋ actor (untyped) の最小コア
- Phase 1: actor-tests からテストクラス単位で移植を広げる
- Phase 2 以降: actor-typed → persistence → remote / cluster → streams の順は
  依存グラフと TestKit 頻度で再評価する
- docs モジュールは移植対象から外す（ドキュメント用コード）

### 3.2 グラフモデル

- ノード = テストクラス（ゴールはノードの部分集合。モジュール単位は粗すぎる）
- 辺は3種を分離する: 実装依存 / テスト基盤依存 / 意味的依存。混ぜない
- ノード状態: 未移植 / red（移植済み・失敗）/ green / 移植しない（人間が固定）
- ロールアップ: テストクラス単位の green 率をモジュール合格率へ畳む。
  manager のゴール完了条件はグラフ上で定義できる形にする
- 機械抽出できるもの（モジュール依存、import 関係、頻度集計）は台帳生成スクリプトの仕事。
  設計判断（粒度・辺の意味・ゴールの切り方・順序ポリシー）だけを人間／トップモデルが担う

### 3.3 クレート構成

決定済み（2026-11-11、ユーザー承認）。詳細と根拠は
`docs/decisions/crate-structure-comparison.md`。

- **案C（写像ベースのハイブリッド）を採る**。ライブラリ本体のモジュールは
  1 対 1 でクレートにする（`fraktor-actor`、`fraktor-actor-typed`、
  `fraktor-testkit`、`fraktor-stream` 等、実質 23 前後）。プラットフォーム／
  バインディング系（osgi、slf4j、serialization-jackson、bench-jmh、
  multi-node-testkit 等）はカテゴリ規則で畳む
- **テストのみのモジュールはクレートにしない**。移植テストは検証対象クレートの
  `tests/` 配下に、ノード1件＝ファイル1件で置く（ノード＝テストファイル＝
  コンパイル単位になる）
- **port & adapter は段階1を既定とする**。各クレート内部を kernel
  （プラットフォーム非依存、Clock / Scheduler 等の port を定義）と adaptor
  （std 実装）に分け、境界は syn checker の port-adaptor 境界ルールで守る。
  no_std のためのクレート分割（段階2）は、要求が確定したクレートだけに適用する

### 3.4 Rust 方針

決定済み（2026-11-11、accepted）:

- **所有権モデルは単独所有＋ハンドル型を既定とする**。詳細と根拠は
  `docs/decisions/ownership-model-arc-overhead.md`（accepted）。
  Arc / Rc は、どうしても共有せざるを得ない場所（制御プレーン、スレッド境界の
  送信端、Weak による戻り辺）に限定する
- **型付けの順序は untyped 先行で確定とする**（2026-11-11、ユーザー）。
  untyped（classic）レイヤーを先に作り、typed レイヤーはその上に作る。
  Pekko 自身の構成の踏襲であり、台帳でも `actor-typed` は `actor` に依存し、
  `actor-typed-tests` は `actor` にも直接依存する。Fable 提案の前提分岐のうち
  typed を正とする分岐（G0b-T / G0c-T）は採らない

方向が出たもの（スパイク第2弾、2026-11-11。詳細は所有権モデル文書）:

- 並列化モデル: シャード内はローカルキュー、境界だけチャネル。効くのは
  シャード数より配置（子は原則として親と同一シャード）。境界コストは
  1件あたり約40〜80 ns で設計の障害にはならない
- mailbox の容量政策: セルごと mailbox ＋上限（設定可能）＋バックプレッシャを
  既定とする。一括予約は既定にしない。上限の既定値とあふれ時の意味論は
  Pekko の mailbox テストで確定する

残る要決定の束:
- 同期 / 非同期: 暫定方針として executor は自前（境界実装は差し替え可能、port 越し）。
  最終決定は最初の縦切りの実測後（承認済み論点14の扱い）
- no_std 対応を要求するか自体は未決定。port & adapter 段階1（3.3）により、
  要求が確定したクレートから段階2（クレート分割）へ上げられる形にしてある
- Pekko の設定体系（HOCON / reference.conf 相当）をどこまで再現するか

### 3.5 ライセンス・運用

- Pekko は Apache-2.0。テスト移植時もライセンスはクリーンだが、
  移植したテストには出典（Pekko v1.7.1 のファイルパス）を台帳とファイル冒頭に残す
- CI は最小から（fmt / clippy / test）。GitHub Actions の消費を抑える設計にする
  （j5ik2o アカウントの Actions 枠は逼迫しているため、schedule の乱発はしない）

## 4. fable-input-fraktor-restart.zip の取り込み方（提案）

対象 zip: `fable-input-fraktor-restart.zip`
SHA-256: `985b361710ccd00ba3dd2ec386b49710067b9cb6c9b0983623fd4b77c4e5efba`
中身5点（展開後 計416,372 bytes、うち ledger.yaml が 397,427 bytes）。

### 4.1 基本方針：zip は「Fable への投入物」であって「リポジトリの設計文書」ではない

- zip のまま、あるいは展開してそのまま commit すると、表紙メモ（Fable 宛ての依頼文）まで
  設計文書の顔をして残り、未承認の前提がハーネス化する。旧 fraktor-rs の失敗の再演になる
- 取り込みは3層に分解する: **凍結スナップショット（来歴）／変換（台帳）／判断の戻し（ADR）**

### 4.2 ファイル別の扱い

| ファイル | 役割 | 取り込み先 |
|---|---|---|
| `ledger.yaml` | 事実層の種。ただしモジュール粒度で、テスト→実装対応は近似（292/1,262） | 凍結保存し、リポジトリ台帳（テストクラス粒度）への変換元にする。手編集しない |
| `summary.md` | 人間向け要約 | `docs/baseline/pekko-v1.7.1/summary.md` として凍結保存 |
| `module-deps.dot` | 台帳からの生成ビュー | 同じ場所に凍結保存。ただし「正」ではなく生成物と明記 |
| `pekko-analysis-brief.md` | 分析手法・手順（SemanticDB/SCIP による厳密化の計画を含む） | 凍結保存＋厳密化フェーズの手順書として参照 |
| `00-cover-memo.md` | Fable 宛ての依頼範囲（判断層5項目） | 設計文書にはしない。依頼範囲の5項目を設計課題リストへ転記し、原物は来歴として凍結保存 |

### 4.3 置き場所（案）

```text
docs/
  baseline/pekko-v1.7.1/     # 凍結スナップショット。ここは原則変更しない
    ledger.yaml  summary.md  module-deps.dot  brief.md  cover-memo.md
    PROVENANCE.md            # zip の SHA-256、生成日、手法と既知の限界を1枚に
  decisions/                 # Fable の提案→人間承認→ADR。承認前は draft と明記
ledger/                      # リポジトリ台帳（テストクラス粒度、ここが進捗の正）
```

- zip バイナリ自体は git に入れない（中身と重複し、差分も読めない）。来歴は PROVENANCE.md の
  ハッシュで担保する。zip 原物は Google Drive / ワークスペース側に保管
- Fable からの回答は鵜呑みにして設計へ直接入れず、`docs/decisions/` に提案として受け、
  人間が承認したものだけが設計設定になる
