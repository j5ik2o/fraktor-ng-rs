**このプロジェクトでの追加（fraktor-ng-rs）:**

標準の testing-review への差分。このレポートは、移植したテストと実装を
Pekko 原典と突き合わせた等価性レビューの結果である。

- APPROVE は、原典と突き合わせて等価性に問題がないと確認できた場合だけ
  書く（遷移条件の「指摘なし」）。指摘（new、persists、reopened）が
  1 件でもあれば REJECT とする（遷移条件の「指摘あり」）
- 原典または移植側を参照できないなどで等価性を確認できなかった範囲は、
  「未確認範囲」に理由つきで書く。その範囲が残る間は APPROVE にしない
- 指摘と未確認範囲の両方がある場合は、指摘を優先して REJECT とする。
  確認できた指摘はすべて書き、未確認範囲も併せて書く
- 指摘が 0 件で未確認範囲が残る場合だけ、結果を BLOCKED と書く（遷移条件の
  「指摘はないが、原典または移植側を確認できず、等価性を判断できない」）
- サマリーの直後に、対象（ノード id、移植テストファイル、実装ファイル）を書く
- 指摘の「根拠」には、原典側の根拠（Pekko v1.7.1 のファイルと該当箇所）と、
  移植側の該当箇所を必ず書く。原典側の根拠を示せない指摘は記録しない。
  例外は設計原則（rich-domain-model）の指摘で、原典根拠の代わりに
  workflow rule `pekko-coding-rules` の該当ルールと移植側の該当箇所を書く
- 指摘の「問題」には、深刻度（意味論のずれ ／ 弱体化 ／ 様式 ／ 設計原則）を含める
- 「確認した観点」の表に、次の 4 行を足す

| 観点 | 結果 | 備考 |
|------|------|------|
| 移植の忠実さ | ✅ | ケース数: triage の実数 {n} に対し移植 {m} |
| 振る舞いの互換 | ✅ | - |
| AI 特有のパターン | ✅ | - |
| 設計原則（rich-domain-model） | ✅ | - |
