## このプロジェクトでの追加（fraktor-ng-rs）

標準の write-tests-first への差分。ここでのテストは新規に考えるもの
ではなく、**Pekko 原典テストの移植**である。

- 対象は triage レポートで指定されたノード1件。原典（Pekko v1.7.1 の
  ファイル）を正として移植する
- 置き場所は検証対象クレートの `tests/` 配下に、ノード1件＝
  ファイル1件。ファイル冒頭に出典（Pekko v1.7.1 のリポジトリ相対
  パス）をコメントで残す
- ケースは triage で数えた実数のとおり全部を移植する。ケースを
  落としたり、アサーションを弱めたりしない。移植できないケースは
  勝手に省かず、報告に「除外提案」として理由つきで残す
  （反映してよいのは、台帳の `cases.excluded` に人間が記録した
  承認済みの除外だけ）
- 未承認の除外提案が 1 件でもあれば、移植完了として先へ進めない。
  遷移条件の「未承認の除外提案がある」を選ぶ（run は needs_human で
  終わり、承認するかどうかは人間が決める）
- Pekko 側のテスト名・ケース分割に対応が追える命名にする
- 時間依存（sleep や eventually 等）は、実時間待ちにせず、port 越しの
  仮想時間で書ける形を優先する。基盤がまだ無い場合はその旨を報告に残す
- 実装がまだ存在しない型・関数への参照は、そのまま書いてよい
  （次の verify_red でコンパイルエラーになることが想定どおりの red）
- テストは本番の振る舞いを呼ぶこと。検証したい意味論（振る舞いの
  差し替えなど）を、テストの中に私有の仕組み（例：テスト内のスタック）
  で作って再現しないこと。本番の API がまだ無い場合は、その API を
  呼ぶテストを書いて verify_red でコンパイルエラー（red）にするのが
  想定どおりの進め方である（G0e の失敗：テスト内スタックで再現した
  ため未実装の挙動が一度も観測されず、赤確認が成立しなかった）
- 台帳の対象ノードの `rust.crate` と `rust.test_file` を記録する
  （後段の機械ゲートが台帳から対象を引くため。status など他の欄は
  変更しない）
- 作成・変更したテストファイルには rustfmt を適用して整形を済ませる
  （例: `rustfmt --edition <ルート Cargo.toml の edition> <ファイル>`）。
  後段の機械ゲート verify_green は `cargo fmt --check` を含むため、
  自分のファイルが整形差分を出さない状態で完了とする

## レポート（test-report）への書き方

レポートは標準の test-report の形式で書く。移植の情報は次の欄に入れる。

- 「完了契約-テスト対応表」の契約は、原典のテストケースを単位にする。
  「由来」には原典のテスト名を書く
- 「作成テスト」の「概要」に台帳のノード id を書く。「テスト数」は
  移植したケース数である
- 除外提案は「未カバー項目」に書く。移植できない理由に加えて、
  人間の承認待ちであることを「後続で必要な確認」に書く

## 作業フェーズの応答への必須行

作業フェーズ（Phase 1）の最終応答の本文に、次の3行を必ず含めてください。
後段の機械判定ステップ（verify_red）は、レポートファイルではなく、
この応答をこの形式で読みます。レポートに書くだけでは届きません。

```
node: {台帳のノード id}
crate: {検証対象のクレート名}
test_file: {作成したテストファイルのパス}
```
