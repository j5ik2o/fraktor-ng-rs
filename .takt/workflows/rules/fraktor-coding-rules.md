Rust のコードやテストを計画、移植、作成、実装、修正、またはレビューする場合は、次の Pekko 移植コーディングルールに従ってください。

これらは verify_green の syn チェッカー（tools/syn-check）で機械判定されるルールです。ゲートで落とされてから直すのではなく、書く時点で守ってください。ルールの正はチェッカーの定義と `tools/syn-check/README.md` で、ここに書くのは事前提示用の要約です。食い違いがあればチェッカー側に合わせてこちらを直します。「暫定」と書いた箇所は、チェッカー側で人間の判断を待っている点です（`tools/syn-check/README.md` の「要判断」）。決まれば変わりえます。

**ファイルと型の配置**

- **type-per-file**：1ファイルに置く `pub` の struct / enum / trait は1つだけ。type alias、union、`pub(crate)` などの限定公開は数えない。cfg で切り替える同名の型は1つと数える。テスト側のファイル（`tests/` 配下、`*_test.rs`）は対象外
- **mod-file**：`mod.rs` は作らない。モジュールは `foo.rs` と `foo/` ディレクトリの階層で表す
- **module-wiring**：再エクスポート（可視性を付けた `use`）は、末端モジュール（子モジュールを持たないモジュール）の直属の親だけが、`pub use child::Type;` の形で行う。`self` / `super` / `crate` を経由した再エクスポート、`as` での付け替え、子モジュールを介さない再エクスポートは書かない。直属の子でないもの（ほかのクレート、`core`、`std`、孫モジュール）からの再エクスポートも書かない。末端モジュールは可視性なしの `mod foo;` で宣言する。`#[path]` と `include!` でモジュールを結線しない。例外は `#[cfg(test)] #[path = "<module>_test.rs"] mod tests;` だけ。`prelude` という名前のモジュールは対象外
- **module-examples**：`crates/<crate>/examples/` に example を置かない（暫定。代わりの置き場所は未定）

**記述の配置**

- **use-placement**：`use` と、本体を持たない `mod` 宣言は、ファイルまたはモジュールの冒頭にまとめる。関数やブロックの中に `use` を書かない。テスト、ベンチ、example のファイルは対象外である（`tests/`、`benches/`、`examples/` の下と、`tests.rs`、`*_test.rs`、`*_tests.rs`。ただし `tests/ui/` の下は対象）。それ以外のファイルでは、`#[cfg(test)]` の付いた宣言やモジュールの中も対象になる
- **tests-location**：`src` 内の単体テストは、対象ファイルと同階層の `*_test.rs` に置き、本体ファイルには `#[cfg(test)] #[path = "<module>_test.rs"] mod tests;` だけを書く。この宣言も `mod` 宣言なので、ファイル末尾ではなく冒頭の `use` / `mod` のまとまりに置く（末尾に置くと use-placement に違反する）。本体ファイルに `mod tests { }`、`#[cfg(test)]` のアイテム、`#[test]` を書かない。テストファイルに `#![cfg(test)]` を書かない（移植テストは対象クレートの `tests/` に置く）

**境界（port & adapter）**

- **port-adaptor-boundary**：adaptor（`src/adaptor.rs` と `src/adaptor/**`）の公開 struct のフィールドに、kernel の具象 API（名前が `Api` で終わる型）を持たせない。kernel の型を、同名の struct の `inner` フィールドで包むこともしない。kernel 側に port（trait）を定義し、adaptor はその trait に依存する（適用範囲は暫定）
- **cfg-std-forbid**：kernel（`src/kernel.rs` と `src/kernel/**`）に `#[cfg(feature = "std")]` と `use std::...` を書かない。`core` か `alloc` を使うか、std に依存するコードを adaptor に移す。`#[cfg(test)]` のコードは対象外（適用範囲は暫定。no_std の要否は未決定）

**命名と文書**

- **ambiguous-suffix**：Manager / Util / Facade / Service / Runtime / Engine で終わる名前を付けない。型、関数、変数、引数、フィールド、モジュール、ファイル名のすべてが対象。テスト側のファイルは対象外
- **rustdoc**：doc コメント（`///` と `//!`）は英語で書く。コードフェンスに `ignore` を付けない

**設計原則（レビューで判定）**

この節はチェッカーの機械判定ではなく、ワークフローの AI レビュー
（等価性レビュー等）で判定する。

- **rich-domain-model**：ドメイン型（struct / enum）は、Scala や Java の
  クラスと同じように、データと振る舞いを持つオブジェクトとして設計する。
  フィールドだけの入れ物にして、ロジックを外の関数やサービス側に置く
  貧血モデルにしない。関数とデータをバラバラにしないこと。Rust には
  メソッド（impl）があるので、振る舞いは型の impl に持たせるのが原則で、
  ドメイン型を受け取って中身を操作する自由関数の集まりにしない。
  検証可能な形で言うと次の 2 点。(1) 生成時の検証を
  型の impl に持つ：不変条件のある型は `new` / `parse` / `from_*` が検証して
  作り、呼び出し側で場当たりに検証しない。(2) その型のデータだけを読んで
  判断・変換するロジックは、外の自由関数ではなくその型の impl に置く。
  公開フィールドの単なるデータ袋と、型の振る舞いの外への漏れは、
  レビューの差し戻し理由になる。純粋なデータ運搬が役割の型
  （設定の読み込み結果、FFI 境界の形など）は理由があれば例外にできるが、
  kernel のドメイン型は原則どおりとする
- **domain-primitive**：ドメインの概念を表す値は、基本型（文字列や
  数値）のまま受け渡しせず、生成の時点で不変条件を確認する専用の型
  （ドメインプリミティブ）にする。これは必須の決まりである（正は
  ddd-principles の方針ページ `knowledge/positions/domain-model-usage-decisions.md`
  の規則 `value-object/type-domain-values/use-a-dedicated-type`）。
  例外は狭く、特別な扱いが必要なく、範囲・長さ・書式の確認も不要で、
  ほかの属性とも関係しない、本当に単純な属性だけである。通常の性能は、
  基本型のままにする理由にはならない。理由は3つある。ドメインモデルは
  ドメインの知識に依存し、基本型はコンピュータの知識であるため、
  ドメインの概念を基本型で表すことは依存先の取り違えであること。
  不変条件と知識を伴う計算を一か所へ集められること。同じ基本型では
  意味の違う値を区別できず起きる取り違えを防げること。不正な値を
  作れないことによるセキュリティの効果は副次効果であり、主たる理由には
  置かない。生の基本型のままドメインの値を受け渡している箇所は、
  レビューで指摘する

**命名（レビューで判定）**

この節はチェッカーの機械判定ではなく、ワークフローの AI レビューで判定する。

- **product-surface-naming**：製品表面（型、モジュール、ファイル、公開 API、設定キー、ワークフローと facet の名前）には移植元の名前を使わない。原典テストのデータ文字列、台帳のノード ID、原典の対応を示すドキュメントコメントは例外とする

**抑制コメント**

チェッカーには抑制の手段がある（`// syn-check: allow(<rule>) -- <理由>` と `// syn-check: allow-file(<rule>) -- <理由>`）。抑制コメントは人間の許可なく足さない。ルールを守れない箇所があれば、コードを直すか、理由を添えて報告する。抑制コメントはチェッカーの出力に一覧として出る。
